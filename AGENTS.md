# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this project is
PyRaya (پیرایہ) is a **reusable, self-contained PySide6 (Qt) text editor widget** for Urdu / Nastaliq (right-to-left) text. It is a drop-in `QWidget` for embedding Urdu text editing in Qt applications — currently PySide6 only.

Current status: **alpha (0.1.0-alpha.7)**. The widget is a `QPlainTextEdit` with RTL layout, right-aligned paragraphs, a configurable Noto font stack (default `Noto Naskh Arabic`), visible whitespace, a dedicated rule-based formatting highlighter, and text regions implemented: spans tagged as `latin` or `roman urdu` (:class:`RegionType`) and rendered with a subtle, type-specific background color, tagged from the right-click context menu, the `Ctrl+1` / `Ctrl+2` keyboard shortcuts, or `setRegionType`. Every character belongs to exactly one region kind at all times — untagged text belongs to `DefaultRegionKind` (RomanUrdu) — each kind's identity is its unique background color (compared including the alpha channel), and clearing regions resets the text to `DefaultRegionKind`. The kind-to-color palette is **per widget** (Q-1 decision): every `PyRaya` copies the module-level `RegionColors` default at construction and owns it — `regionColors()` returns a copy of the widget's palette, and `setRegionColor` maps within the widget alone — so one widget's recolour cannot corrupt another widget's identity map. **`regionsChanged` has one defined meaning** (Q-2 decision): it is emitted once when a region-touching operation invoked through the widget has completed — `setRegionType`, `clearRegions`, a successful `setRegionColor`, a non-empty `setPlainText`, and every roman-input commit that writes text (edge commits write nothing and do not emit); document edits made outside these operations are not inspected and do not emit, which keeps the signal cost-free during typing. A **roman-input overlay** is also implemented and is enabled by default (`setRomanInputEnabled`): an Arabic-script word inside a `roman urdu` region gets a small frameless, non-modal overlay `QLineEdit` matched to the word's geometry — typed roman text is edited there while the document stays Arabic-script, a tier-colored suggestion list (green = exact, orange = edit-distance 1, red = distance 2) is offered below the line edit — flipping above it only when it would not fit below the anchor *and* the space above the anchor is larger than the space below (ties and near-top anchors keep it below; the list is clamped, truncated at the losing side's edge, in either orientation; at most five rows, scrolling so the highlighted row stays visible) — and committing (Space / Enter / typed punctuation — including the Arabic script's own separator marks ؟ ، ؛ ۔ ٫ ٬ ؜, `ArabicScriptSeparators` — or Left/Right at the word's text edges) writes the selected Arabic word plus the separator character to the document tagged as `roman urdu` (a plain Enter commits the word plus a newline; Ctrl+Enter commits the word without one); an edge commit (Left at the visually left edge of the word, Right at the visually right edge) writes nothing and moves the cursor in visual order — to the next word or the previous one — landing at that word's edge facing the active word (Left at its start, Right at its end), and the post-commit resync re-activates the overlay over the landed word (a cursor at the word's end is over the word: `_wordUnderCursor` accepts the run's end); with no adjacent word — the commit lands on a boundary word, whose far side is only whitespace — the overlay is closed and the post-commit resync skipped, so the deactivation sticks and the cursor rests at the boundary edge (Left at the word's end, Right at its start). A Ctrl+Enter commit skips the resync, so a dismissed overlay is not re-triggered and the cursor rests at the inserted word's end until the next trigger (a cursor move, a click, or Ctrl+Space). The overlay is placed in viewport coordinates and re-anchored on widget resize (`PyRaya.resizeEvent`): a resize reflows the right-aligned document without moving the cursor or editing it, so the active overlay is re-placed from its stored anchor (the word's rect, or the seeded cursor anchor) after the base handler updates the viewport and text layout, without re-evaluating activation. The line edit stays pinned to its anchor line in both orientations: only the suggestion list moves — flipping above it when it would not fit below the anchor *and* the space above the anchor is larger than the space below (ties and near-top anchors keep it below, truncated at the viewport's bottom edge instead of painting out of bounds at the top), clamped to whichever side it lands on, and flipping back below when a resize restores the room. Zero-match typed words get a `+ Learn <word>` undefined-word row whose commit is a session no-op that writes the typed roman word. Plain Left/Right arrow keys in the document move the cursor in visual (screen) order, since Qt's default logical movement is flipped in this RTL document; modifier variants keep the logical behavior. The engine wraps `romanalfaz`'s `RomanAlfaz` and `romanWordCommitted` signals each committed word. Assist mode is on by default as well: typing and cursor movement activate the overlay as described; Esc on an active overlay dismisses it and turns assist mode off (the user is left alone: typing and mouse presses no longer activate the overlay) until `Ctrl+Space` in the document turns it back on — over the `roman urdu` word under the cursor with its romanized text, or, with no such word, an empty overlay at the cursor; committing never turns the mode off, and Esc in the document (overlay inactive) is a no-op. `setAssistEnabled(False)` hides a shown overlay, `setAssistEnabled(True)` only marks the mode ready, and re-enabling the feature (`setRomanInputEnabled(True)`) resets assist mode to on. A **display-only spell-check underline** is also implemented and is on by default (`setSpellCheckEnabled`): Arabic-script words belonging to `roman urdu` regions (tagged or the default kind) that the romanalfaz dictionary does not know get a wavy `SpellCheckUnderline` in `SpellCheckUnderlineColor`, painted into the text layout only (invisible to `QTextCursor.charFormat()`, never in the undo stack) — no correction or suggestions. The switch is independent of the roman-input feature (all four flag combinations correct); the two share one lazily created `RomanInputEngine`, and the highlighter invokes it only when a block contains a candidate word (a maximal Arabic run, both ends `roman urdu`), so the engine and its dictionary cold load are created on the first such re-highlight — never for a textless widget — and an unavailable engine (missing dictionary) makes the pass a no-op rather than underlining every word. The spell-checker's correction/suggestion side remains on the **roadmap** (see `README.md`); do not assume it works.

## Conventions
- Use the `src/` layout. The importable package is `pyraya` — import from `pyraya`, **not** `src.pyraya`.
- Naming follows the Qt toolkit: `camelCase` for variables, functions, methods, and signals; `PascalCase` for classes, enum members, and module-level constants (private ones keep the `_` prefix with `PascalCase` casing, e.g. `_Separators`).
- Type hints are required on public functions and classes; the whole project must pass `pyrefly check`.
- Public API must have docstrings (Google-style sections such as `Args:`, with reST cross-references like `:class:`).
- New public symbols must be re-exported from `pyraya/__init__.py` and added to `__all__`.
- New source modules include the copyright banner header used in `pyraya_widget.py`.
- Keep lines within ruff's 100-character limit.
- Keep `ruff check`, `ruff format`, and `pyrefly check` clean before considering work done.
- Keep imports sorted and minimal (ruff `I`).
- Do not add third-party dependencies without updating `pyproject.toml` and re-locking (`uv lock` / `uv sync`).
- Version bumps: change `version` in `pyproject.toml`, run `uv lock`, and update the version string in `README.md`.

## Gotchas
- Instantiating `PyRaya` requires a `QApplication` to exist (see the offscreen test).
- The **Noto** fonts (Noto Naskh Arabic, Noto Nastaliq Urdu, Noto Sans Arabic, …) may not be installed in CI / agent environments — the widget falls back through its font stack and lets Qt substitute; do not assume a specific font is available in automated tests.
- RTL layout is implemented via the widget layout direction and right-aligned blocks; the shaping engine handles Urdu/Arabic script ordering. The Noto fonts may be absent in automated environments, so the rendered font may be a fallback.
- `pydantic` is a declared dependency but is currently unused — reserved for roadmap work; do not build the current API on it. `romanalfaz` backs the roman-input engine: `RomanAlfaz()` must be constructed before calling `addVocabulary`, and `suggest()` returns a **list of per-tier lists**, not a flat list.
- **Never stage IDE/editor files** — `.idea/`, `.vscode/`, and other IDE-specific files are git-ignored and must not be committed.
- Do not hand-edit `uv.lock` — regenerate it with `uv lock`.
- The demo (`uv run pyraya`) opens a real window; automated verification stays limited to the offscreen test suite.
- Qt documents keep an implicit trailing terminator character, so `characterCount()` is one greater than the visible text length. Character-format merges spanning that character are silently dropped — region ranges are clamped to `characterCount() - 1`, and the region lookup for the right-click context menu guards the same boundary, so a right-click on an empty document, or with the cursor at the end of the text, never requests an out-of-range `QTextCursor` position; the scenario-1 typing gate (`_regionKindForTyping`) deliberately admits the document-end position, resolving to the kind of the last real character before the cursor (or `DefaultRegionKind` on an empty document). Region state lives in the document's character formats (background colors), which is why spans survive edits and undo/redo; cleared characters are repainted with the `DefaultRegionKind` background color because a merge cannot restore a `NoBrush` background.
- `QSyntaxHighlighter.setFormat` applies formats to the text **layout**, which Qt merges with the document's character formats at display time — it never modifies the document's character formats (invisible to `QTextCursor.charFormat()` and `QTextBlock.charFormat()`), is re-applied on every re-highlight, and is never recorded in the undo stack. **setFormat replaces the whole per-character layout format, it does not merge** — a background-only `setFormat` over a range wipes the foregrounds previously set for those characters (`self.format(pos)` reads the current per-character layout format back; add the new properties and set the merged format — per uniform run of equal current formats via `_uniformRuns`, the idiom both `_paintDefaultRegions` and `_underlineUnknownWords` use; characters whose current layouts compare equal are rewritten once instead of per character, which writes exactly the formats a per-character loop would). The highlighter's region-maintenance pass therefore paints (merges) the `DefaultRegionKind` background into the layout while preserving the rules' foregrounds — otherwise untagged text falls back to the default black ink, and with visible whitespace the space's designed `#e0e3ff` dot renders as a heavy black mark (`testUntaggedLatinKeepsRuleForegroundUnderDefaultWash`, `testUntaggedWhitespaceKeepsDesignedDotColor`) — but **which** characters it reads the document for is derived run-based (A2): the pass walks the block's format runs (one document-format read per run, via the shared PySide6 block-iteration cast) and skips tagged runs whole, so tagged characters cost no document read, only untagged characters get the per-character read-back merge. Region state itself is stored in the document's character formats (cursor merges). `QSyntaxHighlighter.currentBlock()` is the block accessor in Qt 6 (`current()` does not exist).
- Never make a repaint in response to a document change undoable: undoing it exposes untagged text, the repaint pushes a new command, and Qt clears the redo stack on any new edit, so the original edit becomes unreachable behind an undo/redo ping-pong. The initial block-alignment merge in `__init__` is wrapped in `document().setUndoRedoEnabled(False)` / `(True)` so a fresh widget has no phantom undo command; Qt's `setPlainText` replacement is likewise not recorded in the undo stack.
- PySide6 does not dispatch `QWidget.createPopupMenu` or `QWidget.contextMenuEvent` to Python overrides on `QPlainTextEdit` subclasses (both work only on plain `QWidget`), and does not expose `QClipboard.hasText`. The context menu is therefore handled by connecting to `QAbstractScrollArea.customContextMenuRequested` — emitted by the scroll area's viewport event filter when the policy is `CustomContextMenu` (set in the constructor, which also suppresses Qt's automatic empty popup). The request position arrives in viewport coordinates and is converted with `viewport().mapToGlobal()`. The menu is built on `createStandardContextMenu()` plus the region actions. `QTextCursor.MoveMode.KeepAnchor` is the stub-correct spelling.
- PySide6 delivers the widget-level `QPlainTextEdit.cursorPositionChanged` signal to Python slots **without the int argument** — overlay-sync slots must be argument-free; the document-level `cursorPositionChanged` never fires on cursor moves, and `contentsChanged` fires on typing. Both signals funnel into `_syncOverlay` per keystroke, and the second one coalesces to an early exit while `(cursor position, document revision)` is unchanged (`_syncedOverlayInputs`): a commit resync passes `bypassMouse` and ignores the pair (always storing the current one), and every `_deactivateOverlay` — including the funnel's own word-`None` branch, at the cost of one harmless idempotent re-run — invalidates the pair so a state-changing user decision (mouse press, Esc, feature/assist switch, boundary edge commit) forces the next signal to re-examine; a mouse-release resync stays live through that invalidation.
- `QTextLine.cursorToX(pos)` returns a plain `(x, y)` tuple in PySide6, and `contentOffset().x()/.y()` are floats — round the whole sum (`round(left + offset.x())`) rather than `int(round(x))` to keep pyrefly quiet.
- `QTextLayout.lineForTextPosition(pos)` and `QTextLine.cursorToX(pos)` take **block-local** positions (`0 <= pos <= len(block.text())` — the block text excludes the terminator), not absolute document positions: an absolute position overflows the block's own layout past block 0 (where absolute == local by coincidence), and the engine returns an **invalid `QTextLine`** (null engine, index −1) that PySide6 wraps as **non-`None`** — so an `is None` guard is dead code; the correct guard is `line.isValid()`, and calling `rect()` / `cursorToX()` on an invalid line segfaults (the paragraph-2 crash). Line geometry is **layout-local**: `line.rect().top()` is 0 for the first line of *every* block, `block.layout().position()` is `(0, 0)`, and the `cursorToX` tuple's y is the line's layout-local y — the block's y in the document is not stored in the layout; it comes from `blockBoundingGeometry(block)` in content coordinates and must be added to the line's top before translating with `contentOffset()` into viewport coordinates (Qt's own `cursorForPosition` / `cursorRect` follow this exact model, and `QPlainTextEdit.cursorRect` returns the rect in viewport coordinates — the cross-check used by the second-block geometry tests).
- Wheel events do not bubble from the overlay line edit to the host scroll area: the overlay forwards wheel events directly to the nearest `QAbstractScrollArea` ancestor's `wheelEvent`.
- Walking a block's format runs in PySide6: `QTextBlock.iterator` exposes only `atEnd()` and `fragment()` — there is **no** `increment()`/`next()` (the C++ `operator++` is not mapped), so forward iteration (`for it in block:`) is the only way to advance; and the bundled stubs do not declare `QTextBlock.__iter__`, so pyrefly needs `for it in cast("Iterable[QTextBlock.iterator]", block)`. Fragment positions are document-absolute and a fragment never spans a block separator.
- The 50 k reference text (`tests/fixtures/02-50k-doc.txt`) carries one U+FEFF, which `setPlainText` silently drops — a `setPlainText` round-trip is one character shorter than the Python string. The latency harness strips it at load so the built documents hit their exact character targets.
- Character formats on block-terminator characters (an internal `\n` **and** the trailing document terminator) are silently dropped — so the newline separator of an Enter commit stays untagged (default kind). A span-replacement commit via `insertText` on a selection is counted by `availableUndoSteps()` as two steps (delete + insert) but is undone and redone as a single logical edit; the widget cursor does not follow a document-cursor edit, so a commit calls `setTextCursor(cursor)` explicitly.
- PySide6 cannot map `Suggestion | None` as a `Signal` argument type — the overlay's `committed` signal is declared `Signal(str, object, int, str, int)`, and handlers narrow the second argument with `isinstance(..., Suggestion)`.
- Only `RomanOverlay.setText(roman)` (and key input) refreshes the suggestion rows; raw `overlay.lineEdit().setText(...)` leaves the rows stale. `RomanInputEngine.suggestTiers` returns empty when the engine is unavailable (`available` is False, e.g. `DictionaryNotFoundError` during construction; cold engine load is ~0.2 s).
- The roman-input feature is on by default: an ASCII alphanumeric key pressed with the cursor inside a `roman urdu` region (which includes all untagged text) seeds the overlay and never reaches the document; with the feature disabled (`setRomanInputEnabled(False)`), roman keystrokes type straight into the document and no overlay machinery runs. Assist mode is likewise on by default, and only `_onOverlayCanceled` (the `RomanOverlay.canceled` handler) turns it off — commits and cursor-driven deactivation leave it on — with the gate in two places: the typing-seed condition in `keyPressEvent` (`and self._assistMode`) and the `_syncOverlay` early return (`or not self._assistMode`). `Ctrl+Space` in the document's `keyPressEvent` sets the flag back on and activates the overlay (over the word under the cursor via `_activateOverlay`, or at the cursor via `_activateOverlayAt` with empty text); both flags off means no overlay machinery.
- `_isArabicChar` — the word-run scan backing `_wordUnderCursor`, the spell-check candidate scan, and the visual-order word walk — matches the Arabic script block **minus** `ArabicScriptSeparators`: the Arabic script's own punctuation (؟ ، ؛ ۔ ٫ ٬ ؜) terminates a word run exactly like the Latin marks do, so `کام۔` is the word `کام` followed by the mark `۔`, never one word `کام۔`. The separator-key commit gate (`_Separators` = ASCII `string.punctuation` + space/newline + `ArabicScriptSeparators`) accepts the same marks, so a typed Arabic separator commits word + mark with both tagged — the gate and the boundary scan stay in step through the one public set (re-exported from `pyraya`).
- Word walks are **block-local** (A3): a word run cannot cross a block (the block separator is not Arabic), so `_wordUnderCursor` reads the cursor's own block (`findBlock` + block-local positions, re-based to document coordinates), `_adjacentWord` walks neighbour blocks (`block.position() - 1` backwards, `position() + length()` forwards, with the separator slot treated as `len(text)`), and `_activateOverlay`'s romanize + `_wordRect`'s advance fallback slice the word's own block text — no `toPlainText()` copies remain on the word path (guarded by the whole-document differential `testWordWalksMatchWholeTextReference`, kept one round). Two guards are load-bearing: in `_wordUnderCursor`, `position < 0 or not block.isValid()` returns early because a document-level `contentsChanged` fires *while a `setPlainText` replacement is mid-flight*, when the cursor position reads -1 and `findBlock` returns an invalid block — the old `toPlainText` walk silently read the last character through Python's negative indexing (wrong but crash-free), the block-local rewrite crashes on the empty text (`text[-1]` IndexError) without the guard; in `_adjacentWord`, a `reference` at the document's inclusive terminator end clamps to the last real character (the pre-A3 version crashed with an IndexError there — caught by the differential the moment it was written).
- Qt's default Left/Right arrow keys move in **logical** character order (Left = position−1, Right = position+1), which is visually flipped in this right-to-left document. The widget therefore intercepts plain Left/Right (no modifiers) in `keyPressEvent` and moves the cursor in visual (screen) order — Left advances the position, Right retreats it — clamped to `characterCount() - 1`; Ctrl/Shift variants fall through to Qt's logical default.
- The overlay's roman word renders in **left-to-right character order** even though the overlay widget is right-to-left laid out and right-aligned (the line only grows leftward as it is typed): position 0 is the visually left edge and the text end the visually right edge. So the line edit's Qt-default in-text Left/Right are already visually correct, and its edge-commit triggers stay Left at position 0 / Right at the text end; an in-text cursor-only key (Left/Right/Home with the cursor between the edges) must not rebuild the suggestion rows: a rebuild re-runs the fuzzy search and resets the highlighted suggestion to the top row, so `RomanLineEdit.keyPressEvent` refreshes only when the typed text changed (F-6); only the commit target is visual-order — Left at the visually left edge moves to the **next** word, Right at the visually right edge to the **previous** one, landing at that word's edge facing the active word: Left at its start, Right at its end — and the resync re-activates the overlay over the landed word in every case, because `_wordUnderCursor` now accepts the run's end (a cursor at the word's end is over the word); with no adjacent word — the commit lands on a boundary word, whose far side is only whitespace — the overlay is closed and the resync skipped, so the deactivation sticks and the cursor rests at the boundary edge (Left at the word's end, Right at its start). A Ctrl+Enter commit likewise skips the resync, so a dismissed overlay is not re-triggered and the cursor rests at the inserted word's end.
- The host re-places the overlay on every line-edit `textChanged` (`_onOverlayTextChanged`), so its width tracks the typed text: `RomanLineEdit.sizeHint` is the text advance plus the 6 px margin per side (matching the `SuggestionList` margin convention), and `_placeOverlay` takes the wider of that and the activation width floor — the word's rect width in scenario 2 (the overlay is never narrower than the Arabic word it covers), or the four-roman-character baseline (`4 * lineEdit.fontMetrics().averageCharWidth()`) for a seeded overlay with no word — so the left edge walks with the text while the right edge and the line edit's top stay pinned at the anchor in both orientations (the overlay's top is the line edit's top in the default orientation, the flipped list's top in the flipped one); the flip itself compares the two list-sized spaces — below (`viewportHeight − top − hint.height() + listHint`, the list's bottom edge in the default orientation) and above (`top − 4`, the flipped clamp budget) — flipping only when the list does not fit below *and* the above space is strictly larger, so ties and near-top anchors stay below with the overlay's height clamped to the viewport (the list truncated at the bottom) rather than painting out of bounds at the top; in the flipped orientation the overlay's height is the line edit plus the list clamped to the space above the anchor line, and the line edit is pinned to the anchor line by forcing the overlay's own `QBoxLayout` to resolve for the size just set (`layout().invalidate()` + `layout().activate()` both run while the overlay is hidden), then reading the line edit's settled slot back and shifting the box so the pinning is exact — without the forced activation a re-layout only ever happens for a *visible* parent, so placing a hidden overlay (the click path: a press hides the overlay before the release re-activates it over the word) would answer with the previous word's slots and drag the whole overlay off the word by the slot difference whenever the two words' suggestion lists differ in height. `_syncOverlay` never re-runs while the user edits in the overlay (the document cursor and contents are untouched). When the suggestion list's row count or visibility changes during editing, the overlay's `QVBoxLayout` redistributes the leftover vertical space — QBoxLayout splits it evenly across the layout gaps, which drags the `RomanLineEdit` down away from its top anchor (or, in the flipped orientation, up away from its bottom anchor) (visible at a two-character text, and when the text is empty and the list hides). The overlay's trailing `layout.addStretch()` absorbs all leftover space so the line edit stays pinned to the orientation's outer edge at all times (top in the default, bottom in the flipped); removing it regresses the drift.
- The pinning invariant is absolute: the overlay input stays exactly over the trigger word everywhere and always. `_placeOverlay` pins the overlay's right edge to the word's right edge in both orientations — a word hugging the viewport's right edge (or a typed text wider than the room to its left) clips the overlay on the left rather than pulling the right edge off the word, and a viewport that cannot show the overlay is adjusted (resized or scrolled) by the user, never worked around by moving, clamping, or hiding the overlay away from the word. The active overlay also follows its word on scroll: `PyRaya.__init__` connects `verticalScrollBar().valueChanged` to an argument-free `_onScrollChanged`, which re-places the overlay over its stored anchor; `_ensureOverlay`'s "scrolls with the text automatically" claim is only the small-scroll blit side effect — `QPlainTextEdit`'s viewport `scroll()` moves child widgets with the painted content, but repaint-only jumps and incremental blit drift can leave the overlay a whole line off the word, and only the explicit scroll hook keeps the placement analytical. The hook re-places the overlay while its word is visible — and the off/on-screen decision is the word-rect hit test, never the overlay widget (the overlay reaches further than its word: a flipped suggestion list hangs up into the viewport): in `_repositionActiveOverlay`, the active word's rect — or the seeded anchor line's cursor rect (`QPlainTextEdit.cursorRect(QTextCursor)`) when scenario 1 — is intersected against `viewport().rect()`; a word whose rect is fully outside the viewport deactivates the overlay, and a partially visible word keeps it pinned. The deactivation is two-way: it is a **view suspension**, not a user state — `_suspendedOverlay` remembers `(word, anchorPosition, typedText, documentRevision)`, and the scroll hook and `resizeEvent` dispatch two-way (`_repositionActiveOverlay` when active, `_restoreSuspendedOverlay` when not): a view event that reveals the remembered anchor (a scroll back, a resize grant, a reflow) resumes the overlay as the standard activation (scenario 2 re-romanizes the word, scenario 1 resumes the seeded overlay with its carried-over typed text), with no manual trigger. User decisions outrank the suspension and drop it: every `_deactivateOverlay` funnel call (a mouse press — whose guard therefore also fires over a suspended overlay — Esc/assist-off, the feature switch, boundary-word edge commits, a new activation in `_activateOverlay`/`_activateOverlayAt`), and a document edit while suspended (the remembered revision no longer matches, so the suspension is dropped rather than resumed over text that no longer matches). `_syncOverlay`'s activation is viewport-aware too: a cursor move or keyboard edit landing the cursor on a word that is fully outside the viewport stays quiet (the cursor's position is not a view decision; no popup over an invisible word), and the same-word cursor resync goes through `_repositionActiveOverlay`, so cursor moves honor the hit test and its suspension. The suggestion list's height is also row-quantized: after the forced activation `_placeOverlay` reads the list's actual allocated height and snaps the overlay's height down by `list.height() % list.rowHeight()` (one extra `invalidate()` + `activate()` pass; the `SuggestionList.quantizedHeight` accessor answers the whole-height), so a clamped or truncated placement can never paint a blank strip of list background below its last visible row — the panel ends flush at that row's bottom edge — at the cost of one old artifact: the below-orientation truncation no longer lands the overlay's bottom edge exactly on the viewport's bottom (the row floor wins over the flush fit).
- `RomanOverlay` and `RomanLineEdit` are both mouse-transparent (`Qt.WA_TransparentForMouseEvents`), so `QApplication.widgetAt` over the word returns the document viewport — the document receives real presses, and drags and double-clicks run their default selection; keyboard focus is independent of hit-testing, so the host still calls `setFocus` on the overlay line edit at activation. `PyRaya.mousePressEvent` deactivates the overlay and then sets `_mouseActive`, so `_syncOverlay` early-returns while the button is down (a drag would otherwise reposition the overlay mid-drag, and cross-boundary deactivation would refocus the document); `mouseReleaseEvent` clears the flag after default handling and resyncs — a release on a `roman urdu` word re-activates the overlay (scenario 2) with line-edit focus. The post-commit resync passes `bypassMouse=True`, so the edge-commit cursor jump is still reconciled while the flag is set. Press-point quirk — a press at `_wordRect(...).right()` (1 px inside the exclusive right edge) lands the cursor inside the word (at its start), a press at the visual center of a short word lands after the word (on the trailing space, i.e., at the word's end: the release resync re-activates the overlay over it), and a release at `_wordRect(...).left() + 1` lands at the word's end.
- The spell-check pass invokes the engine provider only after its candidate scan (a maximal Arabic run, both ends `roman urdu`) finds at least one candidate — the scan resolves the ends' kinds from the block's format runs (one document-format read per run; A2), not per candidate. — the engine (and its ~0.2 s dictionary cold load) is created on the first re-highlight containing such a word, never for a textless widget. The laziness is load-bearing: `RomanAlfaz` rebuilds its index on any local `Vocabulary` change, and the pinned wheel hard-asserts `undef == 0` over the counter's keys (a `Vocabulary.add` of a roman key stores the roman key), so constructing the engine eagerly in `PyRaya()` would turn a user's `localDictionary()` edit into an `AssertionError`.
- The venv stubs declare `QTextLayout.FormatRange`'s attributes (`format`, `start`, `length`) as `...` with `# type:` comments that pyrefly does not honor (unlike Pyright), so tests reading `block.layout().formats()` must cast the attributes to their documented runtime types (`QTextCharFormat` / `int`) to stay pyrefly-clean.
