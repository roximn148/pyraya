# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this project is
PyRaya (پیرایہ) is a **reusable, self-contained PySide6 (Qt) text editor widget** for Urdu / Nastaliq (right-to-left) text. It is a drop-in `QWidget` for embedding Urdu text editing in Qt applications — currently PySide6 only.

Current status: **alpha (0.1.0a11)**. The widget is a `QPlainTextEdit` with RTL layout, right-aligned paragraphs, a configurable font stack (default `Baloo Bhaijaan 2` — `PyRayaFonts`'s first installed entry, the Noto Naskh/Nastaliq fonts follow it; nothing installed falls back to the stack's first entry), visible whitespace, and a dedicated rule-based formatting highlighter. Five feature systems sit on top; their contracts are pinned by the test suites below and their mechanics live in Gotchas:

- **Text regions** — region kinds (`RegionType.Native` / `RegionType.RomanUrdu`) stored as an integer property (`RegionKindProperty`) on the document's character formats, tagged from the right-click context menu ("Region: Native" / "Region: Roman Urdu"), the `Ctrl+1` (Native) / `Ctrl+2` (RomanUrdu) shortcuts, or `setRegionType`. Resolution is two steps: a **stored tag wins**, and untagged characters take the widget's seed kind (`SeedRegionKind` = RomanUrdu — read-only, `seedRegionKind()` answers the module value copied in at construction, no setter) — untagged text *acts as* RomanUrdu (tinted, roman-input-active) while Native carries no tint; `clearRegions` removes stored intent.
- **Region-scoped substitution** — the fixed `RegionSubstitutions` table (in `regions.py`, with `substituteChar` / `substituteText` helpers re-exported from `pyraya`; `RomanUrdu`'s entry populated, `Native`'s empty and passing through, the colon deliberately absent) rewrites four punctuation marks (full stop, comma, question mark, semicolon) and the ten Eastern Arabic-Indic digits (0–9 → ۰–۹) to their Urdu forms at the write path, tagged with the region kind.
- **Roman input** (on by default, `setRomanInputEnabled`) — an Arabic-script word inside a RomanUrdu-resolved region activates a small frameless, non-modal overlay `QLineEdit` over the word: typed roman text is edited there while the document stays Arabic-script, and a tier-coloured suggestion list (green = exact, orange = edit-distance 1, red = distance 2) is offered below it — flipped above only when it would not fit below *and* the space above is larger (ties and near-top anchors stay below). A typed word with no exact match gets a trailing `+ [<word>]` undefined-word row (after the fuzzy rows), its label elided to 14 Latin characters. Commits write the Arabic word plus a separator, tagged `roman urdu`; the engine wraps `romanalfaz`'s `RomanAlfaz`, and `romanWordCommitted` signals each committed word. Assist mode (`setAssistEnabled`, on by default) re-triggers the overlay on typing and cursor movement; the full commit matrix, edge-commit, Esc/assist-mode and geometry contracts are pinned in `test_roman_input.py` and documented in Gotchas.
- **Spell-check underline** (on by default, `setSpellCheckEnabled`) — unknown RomanUrdu-resolved words get a display-only wavy underline; no correction or suggestions.
- **Learn words** — one application-wide shared `Vocabulary` + `RomanAlfaz` engine per process (`_SharedEngine` in `roman_input.py`, borrowed by every widget); the host persists learned words by polling `localDictionary().isModified()` and calling `Vocabulary.save`, and the built-in `AddWordDialog` right-click / `+ Learn` paths learn through it.

The spell-checker's correction/suggestion side remains on the **roadmap** (see `README.md`); do not assume it works.

## Conventions
- Use the `src/` layout. The importable package is `pyraya` — import from `pyraya`, **not** `src.pyraya`.
- Naming follows the Qt toolkit: `camelCase` for variables, functions, methods, and signals; `PascalCase` for classes, enum members, and module-level constants (private ones keep the `_` prefix with `PascalCase` casing, e.g. `_Separators`).
- Type hints are required on public functions and classes.
- Public API must have docstrings (Google-style sections such as `Args:`, with reST cross-references like `:class:`).
- New public symbols must be re-exported from `pyraya/__init__.py` and added to `__all__`.
- New source modules include the copyright banner header used in `pyraya_widget.py`.
- Keep lines within ruff's 100-character limit.
- Keep `ruff check`, `ruff format`, and `pyrefly check` clean before considering work done.
- Keep imports sorted and minimal (ruff `I`).
- Do not add third-party dependencies without updating `pyproject.toml` and re-locking (`uv lock` / `uv sync`).
- Commit titles: single line with a short conventional prefix (for example, `feat:`, `fix:`, `ref:`, `chore:`, `docs:`, `ver:`) and a concise summary.
- Version bumps (`CHANGELOG.md` follows Keep a Changelog + SemVer): change `version` in `pyproject.toml`, run `uv lock`, update the version string in `README.md`, and move the Unreleased changes into a new version section dated that day (ISO 8601).

## Gotchas
- Instantiating `PyRaya` requires a `QApplication` to exist (see the offscreen test).
- The **Noto** fonts (Noto Naskh Arabic, Noto Nastaliq Urdu, Noto Sans Arabic, …) may not be installed in CI / agent environments — the widget falls back through its font stack and lets Qt substitute; do not assume a specific font is available in automated tests.
- RTL layout is implemented via the widget layout direction and right-aligned blocks; the shaping engine handles Urdu/Arabic script ordering.
- Verifying a Python interpreter change (downgrade or upgrade) is **`compileall` + an actual import under the target interpreter, not a grep for new tokens**. Grepping for `except*`, PEP 695 `type`, `typing.override`, `assert_type`, `reveal_type`, `TypeForm`, `dataclass_transform` only catches *new-token* grammar and *runtime imports* of new typing names; it structurally misses (a) grammar that introduces no new token — the unparenthesized multi-except `except A, B, C:` is 3.14-only and 3.13 rejects it with `SyntaxError: multiple exception types must be parenthesized` — and (b) runtime annotation evaluation: an unquoted forward ref to a class defined later in the file is a genuine 3.13 import-time `NameError` that `compileall` misses, because annotations are not checked at compile time (3.14 evaluates them lazily per PEP 749; 3.13 evaluates them eagerly at def time). The 2026-11-04 step-1 3.14→3.13 downgrade surfaced exactly both in `src/pyraya/roman_input.py` (the multi-except in `RomanInputEngine.__init__`'s unavailable-engine handler, and the unquoted `RomanOverlay` forward ref in `RomanLineEdit.__init__`) — caught only by the compileall+import fallback, not by the plan's grep.
- `pydantic` is no longer a dependency — it was declared in the initial skeleton, never imported, and removed 2026-11-04; re-add it (with `uv lock`) when the roadmap work that reserved it lands.
- `romanalfaz` backs the roman-input engine: `RomanAlfaz()` must be constructed before calling `addVocabulary`, and `suggest()` returns a **list of per-tier lists**, not a flat list. The engine's default Vocabulary is pyraya's own `qamoos.sym` (`_DefaultVocabulary` in `roman_input.py`), loaded in `RomanInputEngine.__init__` and passed as a starter vocabulary to `RomanAlfaz(vocabularies=[...])` — which skips the bundled `UrduWords5k.sym` fallback — so exactly one Vocabulary is attached by default; a missing or malformed file surfaces as `DictionaryNotFoundError` (unavailable engine), and the `qamoos.sym` data file ships in the wheel.
- **`pyside6-essentials`, not the `pyside6` metapackage** — pyraya imports only `PySide6.QtCore`, `PySide6.QtGui`, and `PySide6.QtWidgets`; `pyside6-essentials` provides the `.pyd` binaries, `PySide6/__init__.py`, and the `.pyi` stubs byte-identical to the metapackage's (same sha256 in the wheel RECORDs), so the metapackage's transitive `pyside6-webengine`, `pyside6-pdf`, and `pyside6-addons` install nothing pyraya uses. Watch the shared-file trap: **every** PySide6 sub-package wheel lists `PySide6/__init__.py` in its RECORD, so uv's uninstall of any one of them deletes the file even while another PySide6 package is still installed — `import PySide6` then still succeeds (namespace package) but `PySide6.__version__` fails with `AttributeError` and the module-level machinery (`Shiboken.replaceModuleDict`, dynamic `__all__`) silently vanishes; the fix is `uv pip install --reinstall pyside6-essentials` (observed 2026-11-04 during the metapackage → essentials switch).
- **romanalfaz learn semantics** — `Vocabulary.isModified()` is a **method** (not an attribute): False at construction, after `save`, and after `load`; True after `add`. `add(word, count=1, isCompleted=False)` marks the word completed in the same mutation — the `isCompleted=True` parameter: exactly one change notification, one `recompileLookup`. A `setCompleted` no-op (the word already holds the requested status) is a **non-mutation**: no notification, `isModified` untouched. `recompileLookup` is **atomic**: a failed `add` leaves the previous index intact, but the word stays in the counter **and** the completed set — a failed add would be persisted on `save`, which is why `learnRomanWord` pre-validates mappability before the mutation. `hasWord` is normalized membership (present since a7, already wrapped by `RomanInputEngine.hasWord` and used by the spell-check pass). - **Roman-input input cap** — `RomanInputEngine.maxInputLength` is `maxRomanWordLength + distance + _InputLengthMargin` (margin 2), read fresh from the engine's `maxRomanWordLength` stat on every `suggestTiers` call, so the cap tracks the collective vocabulary (qamoos plus any attached host `Vocabulary`, including learned words) with no staleness — the stat is recomputed and committed atomically with `symSpell` on every `recompileLookup`, so a cap stale against the index is structurally impossible. `None` (unavailable engine, or an empty dictionary) is treated as 0, giving the floor `distance + margin = 4` (harmless — nothing can match an empty index; pyraya's engine always has qamoos attached, so the stat is always `int` in practice). The cap is internal to the suggestion pathway only: `suggestTiers` truncates the typed word to the cap before calling `RomanAlfaz.suggest` (the single chokepoint both `suggest` and the overlay flow through); the line edit and the commit path are untouched, so a long typed word still commits in full, and the `+ Learn` row's elided label is display-only. Rationale: a typed word longer than the longest dictionary word (M = 12 in both qamoos and UrduWords5k) plus the search depth (distance = 2) plus the margin (2) cannot match any dictionary word, so truncating at M + distance + margin = 16 loses no matchable word; the margin of 2 bounds the miss window to words longer than M + distance + margin AND carrying ≥ 3 removable vowels, which keeps it narrow while still covering the common over-typing pattern (doubled vowels). Cost: the cap bounds the multi-run product growth in the per-keystroke suggest cost (the `one overlay keystroke` row in `tests/test_latency.py` budgets 10 ms); the cost-free region is L ≤ 26 (multi-run growth stays in budget below L = 27) and the freeze boundary is L = 27 (beyond L = 27 the cost leaves budget, so the cap's freeze matters). The single-run plateau (~120 ms at L = 16) is pre-existing a9 behaviour the cap does not address.

- Qt documents keep an implicit trailing terminator character, so `characterCount()` is one greater than the visible text length. Character-format merges spanning that character are silently dropped — region ranges are clamped to `characterCount() - 1`, and the region lookup for the right-click context menu guards the same boundary, so a right-click on an empty document, or with the cursor at the end of the text, never requests an out-of-range `QTextCursor` position; the scenario-1 typing gate (`_regionKindForTyping`) deliberately admits the document-end position, resolving to the kind of the last real character before the cursor (or the seed on an empty document). Region state lives in the document's character formats as the `RegionKindProperty` integer (the resolved kind's `int()`), which is why tags survive edits and undo/redo; clearing regions removes the property (`_batchRemoveTags` applies a cleared copy of each span's format — a merge cannot remove a property), after which every character resolves to the seed again.
- `QSyntaxHighlighter.setFormat` applies formats to the text **layout**, which Qt merges with the document's character formats at display time — it never modifies the document's character formats (invisible to `QTextCursor.charFormat()` and `QTextBlock.charFormat()`), is re-applied on every re-highlight, and is never recorded in the undo stack. **setFormat replaces the whole per-character layout format, it does not merge** — a background-only `setFormat` over a range wipes the foregrounds previously set for those characters (`self.format(pos)` reads the current per-character layout format back; add the new properties and set the merged format — per uniform run of equal current formats via `_uniformRuns`, the idiom both `_paintResolvedKinds` and `_underlineUnknownWords` use; characters whose current layouts compare equal are rewritten once instead of per character, which writes exactly the formats a per-character loop would). The highlighter's tint pass therefore paints (merges) each character's resolved kind's tint into the layout while preserving the rules' foregrounds — resolving per fragment in two steps (stored tag, else the seed) via `resolveRegionKind`, and for colourless kinds (Native) the stretch's background is explicitly **removed** (`clearProperty`), because leaving it alone would let the tint of a previous paint survive a re-tag — the layout format of a long-lived document is the last paint's result, not a clean request — otherwise untagged text would fall back to the default black ink, and with visible whitespace the space's designed `#e0e3ff` dot renders as a heavy black mark (pinned by `test_pyraya.py`'s wash assertions). Region state itself is stored in the document's character formats (cursor merges). `QSyntaxHighlighter.currentBlock()` is the block accessor in Qt 6 (`current()` does not exist).
- `QSyntaxHighlighter.rehighlight()` / `rehighlightBlock()` bump `QTextDocument.revision()` by one **unconditionally** — even a no-op re-highlight (an empty `highlightBlock`) bumps it, while a direct `block.layout().setFormats()` re-write with identical formats does not. Any repaint that must leave the document's revision alone (the palette is view-only, so `setRegionColor`) cannot go through the highlighter: it re-writes the per-block layout formats directly (`_repaintLayoutTint` — a value swap of the background brushes equal to the previous tint), which is also undo-free and signalfree. - Property-only `mergeCharFormat` writes **do** reach the internal block separators (probed: the separator slot between fragments carries the property after a merge spanning it), and `setCharFormat` with a cleared copy removes it there too — that is why `_storedTagRuns` reads the separator slots between fragments, so a tag write carried over a block-spanning selection leaves no misread phantom tags. A block's **stale char format**: Qt updates a block's `charFormat()` only at block creation (`insertBlock` seeds it from the creating cursor's format); later property merges touch the fragments, never the block record — so the Ctrl+Enter continuation rides the stored property with no hook and no write, provided the tag covers the paragraph's trailing whitespace (the same `insertBlock` seeding). - `_isArabicChar` — the word-run scan backing `_wordUnderCursor`, the spell-check candidate scan, and the visual-order word walk — is membership in **`ArabicScriptWordChars`**, the derived table of every letter (`L*`) and combining mark (`M*`) in `ArabicScriptRanges` (Arabic U+0600–06FF, Arabic Supplement U+0750–077F, Arabic Extended-A U+08A0–08FF, and Presentation Forms-A/B U+FB50–FDFF / U+FE70–FEFF): the word class is a definition over Unicode general categories, not a hand-maintained exception list, so digits (`Nd` — U+0660–0669 and U+06F0–06F9), punctuation (`P*`), symbols (`S*`), and format characters (`Cf`) inside those ranges are boundaries. A pasted presentation-form word (`ﻛﺎﻡ`) is therefore still one word, `دوست۵` is `دوست` followed by the digit, and `کام۔` is the word `کام` followed by the mark `۔`, never one word `کام۔`. `ArabicScriptSeparators` is derived the same way (`P*` over the same ranges), so it holds the per-mille and per-ten-thousand signs, the triple dot, the percent sign, the five pointed star, and the ornate parentheses as well as the seven marks the hand list named — and the formatting highlighter's ink rule is built from the same `ArabicScriptRanges` (with an amber rule for U+06F0–06F9 beside the U+0660–0669 one). The invisible joiners (ZWNJ U+200C, ZWJ U+200D, LRM U+200E, RLM U+200F, ALM U+061C) are transparent in `_wordRunAround` through `_continuesWordRun`: a joiner continues a run but is trimmed from both edges, so `ک‌ام` is one word, `‏کام` is the word `کام`, and a run of only joiners is no word at all. `wordRuns` is that same scan run forward: it shares `_continuesWordRun` (membership) and `_trimJoiners` (the edge rule) with `_wordRunAround`, so the point query and the whole-text walk cannot diverge — `testWordRunsAgreesWithThePointQuery` pins it, and it fails if either half is changed in only one of the two. The scan returns the *raw* span, interior joiner included: the widget never rewrites user text, because normalization is a lookup-scope concern, not an editing one — canonicalizing in the buffer would silently alter text under the caret and enter the undo stack. The downstream engine normalizes for it: `RomanAlfaz.hasWord` compares `romanalfaz.urduspell.normalize(word)` against its normalized key set (folding positional and presentation forms, lam-alef ligatures, tatweel, and combining marks — the `urdu-spell` method in `romanalfaz.normalization.NORMALIZATION_METHODS`), and `romanizeArabic` folds through `tafseerUrduAr2Rm`, so `ک‌ام`, `ﻛﺎﻡ`, and `کـام` all reach the dictionary as `کام` and all romanize to `kam`. The separator-key commit gate (`_Separators` = ASCII `string.punctuation` + `string.digits` + space/newline + `ArabicScriptSeparators`) accepts the same marks and every digit, so a typed Arabic separator commits word + mark with both tagged, and a typed digit commits the word with the digit as the separator (substituted to its Eastern Arabic-Indic form in `_writeCommit`; the digit's resync is suppressed in `_commitSeparator` because the digit is a boundary, so the cursor comes to rest past the word's run and a resync would find no word and deactivate the overlay anyway) — the gate and the boundary scan stay in step through the one derived set (`ArabicScriptSeparators`, re-exported from `pyraya` with `ArabicScriptRanges` and `ArabicScriptWordChars`).
- Word walks are **block-local** (A3): a word run cannot cross a block (the block separator is not Arabic), so `_wordUnderCursor` reads the cursor's own block (`findBlock` + block-local positions, re-based to document coordinates), `_adjacentWord` walks neighbour blocks (`block.position() - 1` backwards, `position() + length()` forwards, with the separator slot treated as `len(text)`), and `_activateOverlay`'s romanize + `_wordRect`'s advance fallback slice the word's own block text — no `toPlainText()` copies remain on the word path (the A3 rewrite was once guarded by a whole-document differential, retired after its round per the audit plan; the block-local rule is now pinned by `testAdjacentWordInsideARunReturnsTheContainingRun` and the overlay commit suites). Two guards are load-bearing: in `_wordUnderCursor`, `position < 0 or not block.isValid()` returns early because a document-level `contentsChanged` fires *while a `setPlainText` replacement is mid-flight*, when the cursor position reads -1 and `findBlock` returns an invalid block — the old `toPlainText` walk silently read the last character through Python's negative indexing (wrong but crash-free), the block-local rewrite crashes on the empty text (`text[-1]` IndexError) without the guard; in `_adjacentWord`, a `reference` at the document's inclusive terminator end clamps to the last real character (the pre-A3 version crashed with an IndexError there — caught by the differential the moment it was written).
- Qt's default Left/Right arrow keys move in **logical** character order (Left = position−1, Right = position+1), which is visually flipped in this right-to-left document. The widget therefore intercepts plain Left/Right (no modifiers) in `keyPressEvent` and moves the cursor in visual (screen) order — Left advances the position, Right retreats it — clamped to `characterCount() - 1`; Ctrl/Shift variants fall through to Qt's logical default.
- The overlay's roman word renders in **left-to-right character order** even though the overlay widget is right-to-left laid out and right-aligned (the line only grows leftward as it is typed): position 0 is the visually left edge and the text end the visually right edge. So the line edit's Qt-default in-text Left/Right are already visually correct, and its edge-commit triggers stay Left at position 0 / Right at the text end; an in-text cursor-only key (Left/Right/Home with the cursor between the edges) must not rebuild the suggestion rows: a rebuild re-runs the fuzzy search and resets the highlighted suggestion to the top row, so the row refresh runs in the line edit's `textChanged` handler — which a cursor-only key never fires (F-6) — and precedes the width re-placement, whose width derives from the suggestion list's hint; only the commit target is visual-order — Left at the visually left edge moves to the **next** word, Right at the visually right edge to the **previous** one, landing at that word's edge facing the active word: Left at its start, Right at its end — and the resync re-activates the overlay over the landed word in every case, because `_wordUnderCursor` now accepts the run's end (a cursor at the word's end is over the word); with no adjacent word — the commit lands on a boundary word, whose far side is only whitespace — the overlay is closed and the resync skipped, so the deactivation sticks and the cursor rests at the boundary edge (Left at the word's end, Right at its start). A plain Enter commit likewise skips the resync, so a dismissed overlay is not re-triggered and the cursor rests at the inserted word's end.
- The host rebuilds the suggestion rows and re-places the overlay on every line-edit `textChanged` (`_onOverlayTextChanged`), so its width tracks the typed text: `RomanLineEdit.sizeHint` is the text advance plus the `SuggestionListMargin` margin per side (the shared `SuggestionListMargin` constant, B5 — the list's hint splits the same number), and `_placeOverlay` takes the wider of that and the activation width floor — the word's rect width in scenario 2 (the overlay is never narrower than the Arabic word it covers), or the four-roman-character baseline (`4 * lineEdit.fontMetrics().averageCharWidth()`) for a seeded overlay with no word — so the left edge walks with the text while the right edge and the line edit's top stay pinned at the anchor in both orientations (the overlay's top is the line edit's top in the default orientation, the flipped list's top in the flipped one); the flip itself compares the two list-sized spaces — below (`viewportHeight − top − hint.height() + listHint`, the list's bottom edge in the default orientation) and above (`top − OverlayLayoutSpacing`, the flipped clamp budget — B5's shared `OverlayLayoutSpacing` constant, the gap the overlay's layout, its size hint, and this arithmetic all budget) — flipping only when the list does not fit below *and* the above space is strictly larger, so ties and near-top anchors stay below with the overlay's height clamped to the viewport (the list truncated at the bottom) rather than painting out of bounds at the top; in the flipped orientation the overlay's height is the line edit plus the list clamped to the space above the anchor line, and the line edit is pinned to the anchor line by forcing the overlay's own `QBoxLayout` to resolve for the size just set (`layout().invalidate()` + `layout().activate()` both run while the overlay is hidden), then reading the line edit's settled slot back and shifting the box so the pinning is exact — without the forced activation a re-layout only ever happens for a *visible* parent, so placing a hidden overlay (the click path: a press hides the overlay before the release re-activates it over the word) would answer with the previous word's slots and drag the whole overlay off the word by the slot difference whenever the two words' suggestion lists differ in height. `_syncOverlay` never re-runs while the user edits in the overlay (the document cursor and contents are untouched). When the suggestion list's row count or visibility changes during editing, the overlay's `QVBoxLayout` redistributes the leftover vertical space — QBoxLayout splits it evenly across the layout gaps, which drags the `RomanLineEdit` down away from its top anchor (or, in the flipped orientation, up away from its bottom anchor) (visible at a two-character text, and when the text is empty and the list hides). The overlay's trailing `layout.addStretch()` absorbs all leftover space so the line edit stays pinned to the orientation's outer edge at all times (top in the default, bottom in the flipped); removing it regresses the drift.
- The pinning invariant is absolute: the overlay input stays exactly over the trigger word everywhere and always. `_placeOverlay` pins the overlay's right edge to the word's right edge in both orientations — a word hugging the viewport's right edge (or a typed text wider than the room to its left) clips the overlay on the left rather than pulling the right edge off the word, and a viewport that cannot show the overlay is adjusted (resized or scrolled) by the user, never worked around by moving, clamping, or hiding the overlay away from the word. The active overlay also follows its word on scroll: `PyRaya.__init__` connects `verticalScrollBar().valueChanged` to an argument-free `_onScrollChanged`, which re-places the overlay over its stored anchor; `_ensureOverlay`'s "scrolls with the text automatically" claim is only the small-scroll blit side effect — `QPlainTextEdit`'s viewport `scroll()` moves child widgets with the painted content, but repaint-only jumps and incremental blit drift can leave the overlay a whole line off the word, and only the explicit scroll hook keeps the placement analytical. The hook re-places the overlay while its word is visible — and the off/on-screen decision is the word-rect hit test, never the overlay widget (the overlay reaches further than its word: a flipped suggestion list hangs up into the viewport): in `_repositionActiveOverlay`, the active word's rect — or the seeded anchor line's cursor rect (`QPlainTextEdit.cursorRect(QTextCursor)`) when scenario 1 — is intersected against `viewport().rect()`; a word whose rect is fully outside the viewport deactivates the overlay, and a partially visible word keeps it pinned. The deactivation is two-way: it is a **view suspension**, not a user state — `_suspendedOverlay` remembers `(word, anchorPosition, typedText, documentRevision)`, and the scroll hook and `resizeEvent` dispatch two-way (`_repositionActiveOverlay` when active, `_restoreSuspendedOverlay` when not): a view event that reveals the remembered anchor (a scroll back, a resize grant, a reflow) resumes the overlay as the standard activation (scenario 2 re-romanizes the word, scenario 1 resumes the seeded overlay with its carried-over typed text), with no manual trigger. User decisions outrank the suspension and drop it: every `_deactivateOverlay` funnel call (a mouse press — whose guard therefore also fires over a suspended overlay — Esc/assist-off, the feature switch, boundary-word edge commits, a new activation in `_activateOverlay`/`_activateOverlayAt`), and a document edit while suspended (the remembered revision no longer matches, so the suspension is dropped rather than resumed over text that no longer matches). `_syncOverlay`'s activation is viewport-aware too: a cursor move or keyboard edit landing the cursor on a word that is fully outside the viewport stays quiet (the cursor's position is not a view decision; no popup over an invisible word), and the same-word cursor resync goes through `_repositionActiveOverlay`, so cursor moves honor the hit test and its suspension. The suggestion list's height is also row-quantized: after the forced activation `_placeOverlay` reads the list's actual allocated height and snaps the overlay's height down by `list.height() % list.rowHeight()` (one extra `invalidate()` + `activate()` pass; the `SuggestionList.quantizedHeight` accessor answers the whole-height), so a clamped or truncated placement can never paint a blank strip of list background below its last visible row — the panel ends flush at that row's bottom edge — at the cost of one old artifact: the below-orientation truncation no longer lands the overlay's bottom edge exactly on the viewport's bottom (the row floor wins over the flush fit).
- `RomanOverlay` and `RomanLineEdit` are both mouse-transparent (`Qt.WA_TransparentForMouseEvents`), so `QApplication.widgetAt` over the word returns the document viewport — the document receives real presses, and drags and double-clicks run their default selection; keyboard focus is independent of hit-testing, so the host still calls `setFocus` on the overlay line edit at activation. `PyRaya.mousePressEvent` deactivates the overlay and then sets `_mouseActive`, so `_syncOverlay` early-returns while the button is down (a drag would otherwise reposition the overlay mid-drag, and cross-boundary deactivation would refocus the document); `mouseReleaseEvent` clears the flag after default handling and resyncs — a release on a `roman urdu` word re-activates the overlay (scenario 2) with line-edit focus. The post-commit resync passes `bypassMouse=True`, so the edge-commit cursor jump is still reconciled while the flag is set. Press-point quirk — a press at `_wordRect(...).right()` (1 px inside the exclusive right edge) lands the cursor inside the word (at its start), a press at the visual center of a short word lands after the word (on the trailing space, i.e., at the word's end: the release resync re-activates the overlay over it), and a release at `_wordRect(...).left() + 1` lands at the word's end.
- The spell-check pass invokes the engine provider only after its candidate scan (`wordRuns` over the block — the same walk `PyRaya.wordRuns` exposes; both ends resolving RomanUrdu, stored tag or the seed) finds at least one candidate — the scan resolves the ends' kinds from the block's format runs (one document-format read per run; A2), not per candidate — the engine (and its ~0.3 s dictionary cold load) is created on the first re-highlight containing such a word, never for a textless widget. The laziness is load-bearing: `RomanAlfaz` rebuilds its index on any local `Vocabulary` change, and the pinned wheel hard-asserts `undef == 0` over the counter's keys (a `Vocabulary.add` of a roman key stores the roman key), so constructing the engine eagerly in `PyRaya()` would turn a user's `localDictionary()` edit into an `AssertionError`.
- The venv stubs declare `QTextLayout.FormatRange`'s attributes (`format`, `start`, `length`) as `...` with `# type:` comments that pyrefly does not honor (unlike Pyright): reads must cast the attributes to their documented runtime types (`QTextCharFormat` / `int`), and any assignment to them carries `# pyrefly: ignore [bad-assignment]` (see `_copyFormatRange`) — nothing is assignable to an `Ellipsis`-typed attribute, so a cast does not help there.
- **`QDialogButtonBox` button wiring** — `QDialogButtonBox.clicked` emits `clicked(QAbstractButton*)`: one argument, no `StandardButton` overload, so `_onButtonClicked` takes a single `button` and matches by identity against `self._buttons.button(...)` (a two-argument handler `TypeError`s on every click — caught by `testDialogOkButtonAcceptsAndCancelButtonRejects`, which clicks the real buttons rather than monkeypatching `exec`). In PySide6 6.11.2 and 6.12.0 the box's automatic connection to the parent `QDialog`'s `accept()`/`reject()` does not fire (plain `QDialog` + `ok.click()` leaves the dialog open with `result()` unset), so the explicit handler is load-bearing: without it the dialog would never close. Relatedly, PySide6 *swallows* exceptions raised in Python signal slots (prints them and continues the emission), so a `TypeError`-raising handler can still leave the dialog half-behaving while the traceback only shows up on stderr; and `QAbstractButton.click()` on a **disabled** button emits no `clicked` at all (a dialog test that prefills an unmappable word gets a disabled OK and a silent no-op click — prefill a mappable word, e.g. `قلم`).
