# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this project is
PyRaya (پیرایہ) is a **reusable, self-contained PySide6 (Qt) text editor widget** for Urdu / Nastaliq (right-to-left) text. It is a drop-in `QWidget` for embedding Urdu text editing in Qt applications — currently PySide6 only.

Current status: **alpha (0.1.0-alpha.9)**. The widget is a `QPlainTextEdit` with RTL layout, right-aligned paragraphs, a configurable font stack (default `Baloo Bhaijaan 2` — `PyRayaFonts`'s first installed entry, the Noto Naskh/Nastaliq fonts follow it; nothing installed falls back to the stack's first entry), visible whitespace, a dedicated rule-based formatting highlighter, and text regions implemented: region kinds (:class:`~pyraya.regions.RegionType` — `RegionType.Native` and `RegionType.RomanUrdu`) stored as a custom integer property (`RegionKindProperty`) on the document's character formats, tagged from the right-click context menu ("Region: Native" / "Region: Roman Urdu"), the `Ctrl+1` (Native) / `Ctrl+2` (RomanUrdu) keyboard shortcuts, or `setRegionType`. Resolution is two steps: a **stored tag wins**, and untagged characters take the widget's seed kind (`SeedRegionKind` = RomanUrdu) — untagged text *acts as* RomanUrdu, so untagged text is tinted and roman-input-active while Native carries no tint. The seed is **read-only**: `seedRegionKind()` answers the module value copied into the widget at construction; there is no setter. `clearRegions` removes stored intent — every character resolves to the seed again. A **region-scoped character substitution** is also implemented: a fixed per-`RegionType` 1:1 table (`RegionSubstitutions` in `regions.py`, with `substituteChar` / `substituteText` helpers, re-exported from `pyraya`) rewrites typed Latin characters to their Urdu / Arabic-script equivalents at the write path — the four punctuation marks (full stop, comma, question mark, semicolon) and the ten Eastern Arabic-Indic digits (0–9 → ۰–۹) — so a mapped character lands in the document in its Urdu form, tagged with the region kind. The table is **fixed** (no host API), part of the region model: `RomanUrdu`'s entry is populated, `Native`'s is empty (its characters pass through), and the colon is deliberately absent (Urdu has no dedicated colon codepoint and conventionally keeps the Latin `:`). The substitution is **region-scoped, not feature-scoped** — it holds regardless of the roman-input feature, assist mode, or overlay activation: with no overlay active a mapped character is written directly by the typing gate (`_insertSubstitutedChar`, the character never reaching the default handler); with the overlay active a digit is a committing key (it is in `_Separators`, so the commit gate routes it through `overlay.commit` → `_writeCommit`), landing in its Eastern Arabic-Indic form as the separator, and a typed mark commits as the separator likewise; `_writeCommit` runs the committed string through `substituteText` so the separator and any digit in an undefined-word commit land in their Urdu form while the (already Arabic) dictionary word passes through. Latin letters are not in the table, so they still seed the overlay as before. The kind-to-color palette is **per widget and view-only**: every `PyRaya` copies the module-level `RegionColors` default at construction and owns it — `regionColors()` returns a copy of the widget's palette, `setRegionColor` recolours the widget's tint alone, and the palette never feeds back into identity. The palette colours one kind: RomanUrdu's tint; Native is colourless and a `setRegionColor(Native, …)` is rejected. A recolour repaints the tint in the text layouts **directly** (`_repaintLayoutTint`, a background-brush value swap per block) because it must not bump the document revision — even a no-op `QSyntaxHighlighter.rehighlightBlock` bumps `QTextDocument.revision()` by one, and the palette is view-only. **Tag writes are format-only** (a `mergeCharFormat` property write changes no text, but it is a recorded undo step): each write re-highlights its own blocks (`_rehighlightTags`) and raises `_pendingTagRepaint` so any later `undo()`/`redo()` repairs the tint; each write is exactly one undo step (a batch `clearRegions` replays its span removals inside one `QTextCursor` edit block). **Measured correction** (2026-10-23 review probes, twice): Qt ALSO auto-re-highlights the write and its undo/redo through its own `contentsChange` reactions — the plan's original probe ("format-only writes never re-highlight") does not reproduce on this dependency set — so the explicit pass and the `undo()`/`redo()` overrides are belt-and-braces, kept because the tint guarantee must not rest on an undocumented Qt reaction; the Python `undo()`/`redo()` overrides are dispatched for programmatic `undo()`/`redo()` calls only (the keyboard Ctrl+Z path goes through the widget control's own undo and Qt's auto re-highlight, never through the Python override). **`regionsChanged` has one defined meaning**: it is emitted once when a region-touching operation invoked through the widget has completed — `setRegionType`, `clearRegions`, a non-empty `setPlainText`, and every roman-input commit that writes text (edge commits write nothing and do not emit; a recolouring `setRegionColor` touches no document state and does not emit); document edits made outside these operations are not inspected and do not emit, which keeps the signal cost-free during typing. The **typing gate** reads the resolved kind at the cursor (`_typingKindAt`): a stored tag at or behind the cursor wins; at an *empty* block start the block's own char format governs (Ctrl+Enter continuation — **a Ctrl+Enter at a tagged paragraph's end continues its kind with no hook and no write, provided the tag covers the paragraph's trailing whitespace**, because `insertBlock` seeds the new block from the creating cursor's char format); at a *non-empty* block start the region-semantic kind of the block's first real character governs (a block's `charFormat()` is stale — Qt updates it only at block creation); and past a block's real text the last real character governs. A **roman-input overlay** is also implemented and is enabled by default (`setRomanInputEnabled`): an Arabic-script word inside a RomanUrdu-resolved region gets a small frameless, non-modal overlay `QLineEdit` matched to the word's geometry — typed roman text is edited there while the document stays Arabic-script, a tier-colored suggestion list (green = exact, orange = edit-distance 1, red = distance 2) is offered below the line edit — flipping above it only when it would not fit below the anchor *and* the space above the anchor is larger than the space below (ties and near-top anchors keep it below; the list is clamped, truncated at the losing side's edge, in either orientation; at most five rows, scrolling so the highlighted row stays visible) — and committing (Space / Enter / typed punctuation — including the Arabic script's own separator marks ؟ ، ؛ ۔ ٫ ٬ ؜, `ArabicScriptSeparators` — or Left/Right at the word's text edges) writes the selected Arabic word plus the separator character to the document tagged as `roman urdu` (a plain Enter commits the word without a newline and suppresses the resync — the cursor rests at the word's end, over the word, so the resync would only re-trigger the dismissed overlay; Ctrl+Enter commits the word plus a newline and resyncs; Ctrl+Up / Ctrl+Down — exact-Ctrl Up/Down on the active overlay, every other Up/Down staying list navigation — commit the word bare and move the document cursor one line up/down in the commit's `finally` block after the `_committing` flag clears, so the landing goes through the normal assist rules: a roman-urdu word under the landing cursor re-activates the overlay, a bare position stays quiet); an edge commit (Left at the visually left edge of the word, Right at the visually right edge) writes nothing and moves the cursor in visual order — to the next word or the previous one — landing at that word's edge facing the active word (Left at its start, Right at its end), and the post-commit resync re-activates the overlay over the landed word (a cursor at the word's end is over the word: `_wordUnderCursor` accepts the run's end); with no adjacent word — the commit lands on a boundary word, whose far side is only whitespace — the overlay is closed and the post-commit resync skipped, so the deactivation sticks and the cursor rests at the boundary edge (Left at the word's end, Right at its start). One ruled B2 consequence: a seed anchored *inside* a run (reachable — the ASCII typing gate is region-kind-only — when the overlay is inactive over a mid-run cursor, e.g. after a deactivation that stays put) edge-commits onto that run's facing edge instead of staying put, and the resync re-activates the overlay over the same word (`testEdgeCommitFromMidRunSeedLandsOnTheRunEdge`). A plain Enter commit skips the resync, so a dismissed overlay is not re-triggered and the cursor rests at the inserted word's end until the next trigger (a cursor move, a click, or Ctrl+Space). The overlay is placed in viewport coordinates and re-anchored on widget resize (`PyRaya.resizeEvent`): a resize reflows the right-aligned document without moving the cursor or editing it, so the active overlay is re-placed from its stored anchor (the word's rect, or the seeded cursor anchor) after the base handler updates the viewport and text layout, without re-evaluating activation. The line edit stays pinned to its anchor line in both orientations: only the suggestion list moves — flipping above it when it would not fit below the anchor *and* the space above the anchor is larger than the space below (ties and near-top anchors keep it below, truncated at the viewport's bottom edge instead of painting out of bounds at the top), clamped to whichever side it lands on, and flipping back below when a resize restores the room. Typed words with no exact (tier-0) match get a trailing `+ [<word>]` undefined-word row (after any fuzzy-match rows) whose commit is a session no-op that writes the typed roman word; the label is display-only and elides input above 8 characters to its first and last 4 with `..` between (capping the row at 14 Latin characters, and thus the suggestion list's maximum width). Plain Left/Right arrow keys in the document move the cursor in visual (screen) order, since Qt's default logical movement is flipped in this RTL document; modifier variants keep the logical behavior. The engine wraps `romanalfaz`'s `RomanAlfaz` — with the package's own `qamoos.sym` wordlist as the default Vocabulary, replacing the bundled `UrduWords5k.sym` — and `romanWordCommitted` signals each committed word. Assist mode is on by default as well: typing and cursor movement activate the overlay as described; Esc on an active overlay dismisses it only — assist stays on, so typing and cursor movement re-trigger the overlay by the normal rules — while Ctrl+Esc (the exact Ctrl mask) dismisses it and turns assist mode off (the user is left alone: typing and mouse presses no longer activate the overlay) until `Ctrl+Space` in the document turns it back on — over the `roman urdu` word under the cursor with its romanized text, or, with no such word, an empty overlay at the cursor; committing never turns the mode off, Esc in the document (overlay inactive) is a no-op, and Ctrl+Esc in the document turns assist off directly, balancing `Ctrl+Space`'s re-entry (the two Esc paths are mutually exclusive by focus: an active overlay holds focus in the line edit). `setAssistEnabled(False)` hides a shown overlay, `setAssistEnabled(True)` only marks the mode ready, and re-enabling the feature (`setRomanInputEnabled(True)`) resets assist mode to on. A **display-only spell-check underline** is also implemented and is on by default (`setSpellCheckEnabled`): Arabic-script words belonging to `roman urdu` regions (tagged or the default kind) that the romanalfaz dictionary does not know get a wavy `SpellCheckUnderline` in `SpellCheckUnderlineColor`, painted into the text layout only (invisible to `QTextCursor.charFormat()`, never in the undo stack) — no correction or suggestions. The switch is independent of the roman-input feature (all four flag combinations correct); the two share one lazily created `RomanInputEngine`, and the highlighter invokes it only when a block contains a candidate word (a `wordRuns` span, both ends `roman urdu`), so the engine and its dictionary cold load are created on the first such re-highlight — never for a textless widget — and an unavailable engine (missing dictionary) makes the pass a no-op rather than underlining every word. A **learn-word** feature is also implemented: one application-wide shared `Vocabulary` **and** one shared `RomanAlfaz` engine, held in the module-level `_SharedEngine` holder (`roman_input.py`; the module-level `_sharedEngine` singleton, created once per process) — every `PyRaya` widget borrows both (`localDictionary()` and `romanEngine()` return the shared instances), so one `Vocabulary.add` triggers exactly one `recompileLookup` regardless of widget count and the ~0.3 s dictionary cold load happens at most once per process. `_SharedEngine.reset()` is the test-only seam, exercised by the autouse `shared_engine` fixture in `tests/conftest.py`, so every test — in every module — gets a fresh holder and pays the cold load per test exactly as per-widget cold loads did before. `RomanInputEngine.learnRomanWord(arabicWord)` validates mappability **before** the mutation (`tafseerUrduAr2Rm` must return `undef == 0`, because the recompile the mutation triggers hard-asserts `undef == 0` and names the offending word), then `add(arabicWord, isCompleted=True)` — one mutation, one change notification, one `recompileLookup` — and the word lands in `completed` so the host's `Vocabulary.save` persists it; `AssertionError` when no Vocabulary is attached or the word is unmappable, and `add` is idempotent (a retry increments the count, never duplicates the entry). The built-in `AddWordDialog` is pure UI: an editable Arabic-script word field pre-filled with the trigger word, a read-only roman preview, live mappability feedback (OK enabled only while the field is non-empty **and** mappable), and it never mutates the Vocabulary — the widget owns the learn, and the built-in path re-opens the dialog on `AssertionError` (the mappability pre-validation is belt-and-braces behind the dialog's live feedback) with the user's text until they accept or cancel. `setAddWordHandler(handler)` installs a host callable `(trigger: str) -> str | None` in place of the built-in dialog — the trigger is the Arabic word for the right-click trigger, the typed roman for the `+ Learn` row; `None` restores the built-in dialog. `_learnDialog(trigger, prefill="")` learns the accepted word internally on both paths (handler and built-in dialog); `_learnWord(word)` is `learnRomanWord` + a whole-document re-highlight so the spell-check underline for the word clears immediately, then `wordAdded = Signal(str)` fires after each successful learn. The right-click "Add to dictionary" action appears over an unknown RomanUrdu-resolved word — `_learnCandidate`: no selection, the `_wordUnderCursor` maximal Arabic run, `hasWord` false — and commits through the dialog (`_addToDictionary`); the `+ Learn` row commits through the dialog too: OK writes the chosen Arabic word (learned inside `_learnDialog`), Cancel is the session no-op (the typed roman as-is), and edge commits (Left/Right) stay dialog-free. Both learn entry points seed the dialog's field with the widget's `_wordTextAtCursor()` — the `_wordUnderCursor` run sliced out of its own block, the same span every other consumer resolves — so the right-click trigger arrives holding the clicked word and the `+ Learn` row arrives holding the word being romanized (empty only when the cursor rests on no word, e.g. a `Ctrl+Space` seeded overlay); the roman preview is the `hint`, and a host `setAddWordHandler` replaces the dialog entirely, prefill and all. The host contract: persistence is the host's job — it polls `localDictionary().isModified()` (a read-only method on `Vocabulary`: False at construction, after `save`, and after `load`; True after a learn) and calls `Vocabulary.save` on the shared Vocabulary; PyRaya never wraps `save`. Startup load is `Vocabulary.load(file)` standalone (bulk, no recompile storm), then handed to the holder via `replaceVocabulary` — populate-before-attaching, so the engine is built on the loaded Vocabulary with exactly one recompile. The spell-checker's correction/suggestion side remains on the **roadmap** (see `README.md`); do not assume it works.

## Conventions
- Use the `src/` layout. The importable package is `pyraya` — import from `pyraya`, **not** `src.pyraya`.
- Naming follows the Qt toolkit: `camelCase` for variables, functions, methods, and signals; `PascalCase` for classes, enum members, and module-level constants (private ones keep the `_` prefix with `PascalCase` casing, e.g. `_Separators`).
- Type hints are required on public functions and classes; the whole project must pass `pyrefly check`.
- Public API must have docstrings (Google-style sections such as `Args:`, with reST cross-references like `:class:`).
- New public symbols must be re-exported from `pyraya/__init__.py` and added to `__all__`.
- New source modules include the copyright banner header used in `pyraya_widget.py`.
- Keep lines within ruff's 100-character limit.
- Keep `ruff check`, `ruff format`, and `pyrefly check` clean before considering work done.
- Keep imports sorted and minimal (ruff `I`).
- Do not add third-party dependencies without updating `pyproject.toml` and re-locking (`uv lock` / `uv sync`).
- Version bumps: change `version` in `pyproject.toml`, run `uv lock`, update the version string in `README.md`, and move `CHANGELOG.md`'s Unreleased changes into a new version section dated that day (ISO 8601).

## Gotchas
- Instantiating `PyRaya` requires a `QApplication` to exist (see the offscreen test).
- The **Noto** fonts (Noto Naskh Arabic, Noto Nastaliq Urdu, Noto Sans Arabic, …) may not be installed in CI / agent environments — the widget falls back through its font stack and lets Qt substitute; do not assume a specific font is available in automated tests.
- RTL layout is implemented via the widget layout direction and right-aligned blocks; the shaping engine handles Urdu/Arabic script ordering. The Noto fonts may be absent in automated environments, so the rendered font may be a fallback.
- `pydantic` is a declared dependency but is currently unused — reserved for roadmap work; do not build the current API on it. `romanalfaz` backs the roman-input engine: `RomanAlfaz()` must be constructed before calling `addVocabulary`, and `suggest()` returns a **list of per-tier lists**, not a flat list. The engine's default Vocabulary is pyraya's own `qamoos.sym` (`_DefaultVocabulary` in `roman_input.py`), loaded in `RomanInputEngine.__init__` and passed as a starter vocabulary to `RomanAlfaz(vocabularies=[...])` — which skips the bundled `UrduWords5k.sym` fallback — so exactly one Vocabulary is attached by default; a missing or malformed file surfaces as `DictionaryNotFoundError` (unavailable engine), and the `qamoos.sym` data file ships in the wheel.
- **romanalfaz 0.1.0a10 learn semantics** — `Vocabulary.isModified()` is a **method** (not an attribute): False at construction, after `save`, and after `load`; True after `add`. `add(word, count=1, isCompleted=False)` marks the word completed in the same mutation — the `isCompleted=True` parameter: exactly one change notification, one `recompileLookup`. A `setCompleted` no-op (the word already holds the requested status) is a **non-mutation**: no notification, `isModified` untouched. `recompileLookup` is **atomic**: a failed `add` leaves the previous index intact, but the word stays in the counter **and** the completed set — a failed add would be persisted on `save`, which is why `learnRomanWord` pre-validates mappability before the mutation. `hasWord` is normalized membership (present since a7, already wrapped by `RomanInputEngine.hasWord` and used by the spell-check pass). The shared holder is the module-level `_SharedEngine` singleton in `roman_input.py` (created once per process; the test-only `reset()` seam is exercised by the autouse `shared_engine` fixture in `tests/conftest.py`, so every test — in every module — gets a fresh holder and pays the ~0.3 s dictionary cold load per test exactly as per-widget cold loads did before). a9 is a performance release: `romanalfaz.engine` is byte-identical to a8 (so every fact above holds), `exceptions.py` adds `MaxVowelRunExceededError` (defensive, direct `findVowelCombos` misuse only), and `tafseerUrduRm2Rm`'s step 09 now truncates consecutive-vowel runs beyond `MAX_CONSECUTIVE_VOWELS = 8` — the only behavioural change, reachable from pyraya only indirectly through `RomanAlfaz.suggest` on 9+-vowel input (pyraya's own `tafseerUrduAr2Rm` calls are unaffected). a10 adds the `minRomanWordLength` / `maxRomanWordLength` statistics — the min/max character length of the encoded roman words in the aggregate dictionary, `None` when the dictionary is empty — recomputed from the aggregate vocabulary on every `recompileLookup` and committed atomically at its stage 5 alongside `symSpell`; surface additions only, no behavioural change to the existing API.
- **Roman-input input cap** — `RomanInputEngine.maxInputLength` is `maxRomanWordLength + distance + _InputLengthMargin` (margin 2), read fresh from the engine's `maxRomanWordLength` stat on every `suggestTiers` call, so the cap tracks the collective vocabulary (qamoos plus any attached host `Vocabulary`, including learned words) with no staleness — the stat is recomputed and committed atomically with `symSpell` on every `recompileLookup`, so a cap stale against the index is structurally impossible. `None` (unavailable engine, or an empty dictionary) is treated as 0, giving the floor `distance + margin = 4` (harmless — nothing can match an empty index; pyraya's engine always has qamoos attached, so the stat is always `int` in practice). The cap is internal to the suggestion pathway only: `suggestTiers` truncates the typed word to the cap before calling `RomanAlfaz.suggest` (the single chokepoint both `suggest` and the overlay flow through); the line edit and the commit path are untouched, so a long typed word still commits in full, and the `+ Learn` row's elided label is display-only. Rationale: a typed word longer than the longest dictionary word (M = 12 in both qamoos and UrduWords5k) plus the search depth (distance = 2) plus the margin (2) cannot match any dictionary word, so truncating at M + distance + margin = 16 loses no matchable word; the margin of 2 bounds the miss window to words longer than M + distance + margin AND carrying ≥ 3 removable vowels, which keeps it narrow while still covering the common over-typing pattern (doubled vowels). Cost: the cap bounds the multi-run product growth in the per-keystroke suggest cost (the `one overlay keystroke` row in `tests/test_latency.py` budgets 10 ms); the cost-free region is L ≤ 26 (multi-run growth stays in budget below L = 27) and the freeze boundary is L = 27 (beyond L = 27 the cost leaves budget, so the cap's freeze matters). The single-run plateau (~120 ms at L = 16) is pre-existing a9 behaviour the cap does not address.
- **Never stage IDE/editor files** — `.idea/`, `.vscode/`, and other IDE-specific files are git-ignored and must not be committed.
- Do not hand-edit `uv.lock` — regenerate it with `uv lock`.
- The demo (`uv run pyraya`) opens a real window; automated verification stays limited to the offscreen test suite.
- Qt documents keep an implicit trailing terminator character, so `characterCount()` is one greater than the visible text length. Character-format merges spanning that character are silently dropped — region ranges are clamped to `characterCount() - 1`, and the region lookup for the right-click context menu guards the same boundary, so a right-click on an empty document, or with the cursor at the end of the text, never requests an out-of-range `QTextCursor` position; the scenario-1 typing gate (`_regionKindForTyping`) deliberately admits the document-end position, resolving to the kind of the last real character before the cursor (or the seed on an empty document). Region state lives in the document's character formats as the `RegionKindProperty` integer (the resolved kind's `int()`), which is why tags survive edits and undo/redo; clearing regions removes the property (`_batchRemoveTags` applies a cleared copy of each span's format — a merge cannot remove a property), after which every character resolves to the seed again.
- `QSyntaxHighlighter.setFormat` applies formats to the text **layout**, which Qt merges with the document's character formats at display time — it never modifies the document's character formats (invisible to `QTextCursor.charFormat()` and `QTextBlock.charFormat()`), is re-applied on every re-highlight, and is never recorded in the undo stack. **setFormat replaces the whole per-character layout format, it does not merge** — a background-only `setFormat` over a range wipes the foregrounds previously set for those characters (`self.format(pos)` reads the current per-character layout format back; add the new properties and set the merged format — per uniform run of equal current formats via `_uniformRuns`, the idiom both `_paintResolvedKinds` and `_underlineUnknownWords` use; characters whose current layouts compare equal are rewritten once instead of per character, which writes exactly the formats a per-character loop would). The highlighter's tint pass therefore paints (merges) each character's resolved kind's tint into the layout while preserving the rules' foregrounds — resolving per fragment in two steps (stored tag, else the seed) via `resolveRegionKind`, and for colourless kinds (Native) the stretch's background is explicitly **removed** (`clearProperty`), because leaving it alone would let the tint of a previous paint survive a re-tag — the layout format of a long-lived document is the last paint's result, not a clean request — otherwise untagged text would fall back to the default black ink, and with visible whitespace the space's designed `#e0e3ff` dot renders as a heavy black mark (`testUntaggedLatinKeepsRuleForegroundUnderKindTint`, `testUntaggedWhitespaceKeepsDesignedDotColor`). Region state itself is stored in the document's character formats (cursor merges). `QSyntaxHighlighter.currentBlock()` is the block accessor in Qt 6 (`current()` does not exist).
- `QSyntaxHighlighter.rehighlight()` / `rehighlightBlock()` bump `QTextDocument.revision()` by one **unconditionally** — even a no-op re-highlight (an empty `highlightBlock`) bumps it, while a direct `block.layout().setFormats()` re-write with identical formats does not. Any repaint that must leave the document's revision alone (the palette is view-only, so `setRegionColor`) cannot go through the highlighter: it re-writes the per-block layout formats directly (`_repaintLayoutTint` — a value swap of the background brushes equal to the previous tint), which is also undo-free and signalfree. Relatedly, PySide6 does not map `QTextDocument.beginEditBlock`/`endEditBlock` — an edit block must open through a `QTextCursor` (`_batchRemoveTags` replays its span removals inside one throwaway cursor's block).
- Property-only `mergeCharFormat` writes **do** reach the internal block separators (probed: the separator slot between fragments carries the property after a merge spanning it), and `setCharFormat` with a cleared copy removes it there too — that is why `_storedTagRuns` reads the separator slots between fragments, so a tag write carried over a block-spanning selection leaves no misread phantom tags. But an inserted newline (a Ctrl+Enter commit's separator) is injected untagged: character formats on block-terminator characters are silently dropped at insertion, so the separator resolves to the seed. A block's **stale char format**: Qt updates a block's `charFormat()` only at block creation (`insertBlock` seeds it from the creating cursor's format); later property merges touch the fragments, never the block record — so the Ctrl+Enter continuation rides the stored property with no hook, but a *non-empty* block start must resolve the kind of its first real character (`_typingKindAt`), not read the stale block format.
- Never make a repaint in response to a document change undoable: undoing it exposes untagged text, the repaint pushes a new command, and Qt clears the redo stack on any new edit, so the original edit becomes unreachable behind an undo/redo ping-pong. The tag writes are deliberately recorded (format-only — one undo step per write; a batch removal one) and their repaint is NOT: `_pendingTagRepaint` remembers that a tag write entered the history so a later `undo()`/`redo()` of that command repairs its blocks' tint with the never-recorded re-highlight. Measured (2026-10-23 review probes): Qt auto-re-highlights the write and its undo/redo anyway, so the flag is the redundant layer, and it is consumed by whichever `undo()`/`redo()` runs first — a "tag; unrelated edit; undo" sequence consumes it on the unrelated command (invisible today because of Qt's auto re-highlight, but the repair hierarchy is: Qt's reaction first, the flag second). The initial block-alignment merge in `__init__` is wrapped in `document().setUndoRedoEnabled(False)` / `(True)` so a fresh widget has no phantom undo command; Qt's `setPlainText` replacement is likewise not recorded in the undo stack.
- PySide6 does not dispatch `QWidget.createPopupMenu` or `QWidget.contextMenuEvent` to Python overrides on `QPlainTextEdit` subclasses (both work only on plain `QWidget`), and does not expose `QClipboard.hasText`. The context menu is therefore handled by connecting to `QAbstractScrollArea.customContextMenuRequested` — emitted by the scroll area's viewport event filter when the policy is `CustomContextMenu` (set in the constructor, which also suppresses Qt's automatic empty popup). The request position arrives in viewport coordinates and is converted with `viewport().mapToGlobal()`. The menu is built on `createStandardContextMenu()` plus the region actions. `QTextCursor.MoveMode.KeepAnchor` is the stub-correct spelling.
- PySide6 delivers the widget-level `QPlainTextEdit.cursorPositionChanged` signal to Python slots **without the int argument** — overlay-sync slots must be argument-free; the document-level `cursorPositionChanged` never fires on cursor moves, and `contentsChanged` fires on typing. Both signals funnel into `_syncOverlay` per keystroke, and the second one coalesces to an early exit while `(cursor position, document revision)` is unchanged (`_syncedOverlayInputs`): a commit resync passes `bypassMouse` and ignores the pair (always storing the current one), and every `_deactivateOverlay` — including the funnel's own word-`None` branch, at the cost of one harmless idempotent re-run — invalidates the pair so a state-changing user decision (mouse press, Esc, feature/assist switch, boundary edge commit) forces the next signal to re-examine; a mouse-release resync stays live through that invalidation.
- `QTextLine.cursorToX(pos)` returns a plain `(x, y)` tuple in PySide6, and `contentOffset().x()/.y()` are floats — round the whole sum (`round(left + offset.x())`) rather than `int(round(x))` to keep pyrefly quiet.
- `QTextLayout.lineForTextPosition(pos)` and `QTextLine.cursorToX(pos)` take **block-local** positions (`0 <= pos <= len(block.text())` — the block text excludes the terminator), not absolute document positions: an absolute position overflows the block's own layout past block 0 (where absolute == local by coincidence), and the engine returns an **invalid `QTextLine`** (null engine, index −1) that PySide6 wraps as **non-`None`** — so an `is None` guard is dead code; the correct guard is `line.isValid()`, and calling `rect()` / `cursorToX()` on an invalid line segfaults (the paragraph-2 crash). Line geometry is **layout-local**: `line.rect().top()` is 0 for the first line of *every* block, `block.layout().position()` is `(0, 0)`, and the `cursorToX` tuple's y is the line's layout-local y — the block's y in the document is not stored in the layout; it comes from `blockBoundingGeometry(block)` in content coordinates and must be added to the line's top before translating with `contentOffset()` into viewport coordinates (Qt's own `cursorForPosition` / `cursorRect` follow this exact model, and `QPlainTextEdit.cursorRect` returns the rect in viewport coordinates — the cross-check used by the second-block geometry tests).
- Wheel events do not bubble from the overlay line edit to the host scroll area: the overlay forwards wheel events directly to the nearest `QAbstractScrollArea` ancestor's `wheelEvent`.
- Walking a block's format runs in PySide6: `QTextBlock.iterator` exposes only `atEnd()` and `fragment()` — there is **no** `increment()`/`next()` (the C++ `operator++` is not mapped), so forward iteration (`for it in block:`) is the only way to advance; and the bundled stubs do not declare `QTextBlock.__iter__`, so pyrefly needs `for it in cast("Iterable[QTextBlock.iterator]", block)`. Fragment positions are document-absolute and a fragment never spans a block separator.
- The 50 k reference text (`tests/fixtures/02-50k-doc.txt`) carries one U+FEFF, which `setPlainText` silently drops — a `setPlainText` round-trip is one character shorter than the Python string. The latency harness strips it at load so the built documents hit their exact character targets.
- Character formats on block-terminator characters (an internal `\n` **and** the trailing document terminator) are silently dropped — so the newline separator of a Ctrl+Enter commit resolves to the seed. A span-replacement commit via `insertText` on a selection is counted by `availableUndoSteps()` as two steps (delete + insert) but is undone and redone as a single logical edit; the widget cursor does not follow a document-cursor edit, so a commit calls `setTextCursor(cursor)` explicitly.
- PySide6 cannot map `Suggestion | None` as a `Signal` argument type — the overlay's `committed` signal is declared `Signal(str, object, int, str, int)`, and handlers narrow the second argument with `isinstance(..., Suggestion)`.
- The overlay's own `textChanged` handler (connected in `RomanOverlay.__init__`, before the host's `_ensureOverlay` hook, so it runs before every host re-placement) refreshes the suggestion rows on every line-edit text change — a raw `overlay.lineEdit().setText(...)` refreshes them too — and a cursor-only key fires no `textChanged`, so it rebuilds neither. `RomanInputEngine.suggestTiers` returns empty when the engine is unavailable (`available` is False, e.g. `DictionaryNotFoundError` during construction; cold engine load is ~0.3 s).
- The roman-input feature is on by default: an ASCII alphanumeric key pressed with the cursor inside a RomanUrdu-resolved region (which includes all untagged text) seeds the overlay and never reaches the document; with the feature disabled (`setRomanInputEnabled(False)`), roman keystrokes type straight into the document and no overlay machinery runs. Assist mode is likewise on by default, and only `_onOverlayCanceled` (the `RomanOverlay.canceled` handler — the signal carries the Esc key's `Qt.KeyboardModifiers` value, a plain Esc 0 and a Ctrl+Esc the Control value, so the handler turns the flag off only on the exact Ctrl mask) turns it off — commits and cursor-driven deactivation leave it on — with the gate in two places: the typing-seed condition in `keyPressEvent` (`and self._assistMode`) and the `_syncOverlay` early return (`or not self._assistMode`). `Ctrl+Space` in the document's `keyPressEvent` sets the flag back on and activates the overlay (over the word under the cursor via `_activateOverlay`, or at the cursor via `_activateOverlayAt` with empty text); `Ctrl+Esc` in the document's `keyPressEvent` (the exact Ctrl mask) turns the flag off and deactivates the overlay; both flags off means no overlay machinery. Two plain `Esc` presses within `EscDoubleTapInterval` also turn assist mode off, irrespective of whether the overlay is shown: `_lastEscAt` records `time.monotonic()` on every plain Esc (both the overlay path in `_onOverlayCanceled` and the document path in `keyPressEvent`), and the second plain Esc within the interval sets the flag off and resets the timestamp — a single press, or one out of interval, only records; `Ctrl+Esc` and `Shift+Esc` are not tap candidates, so they cannot form a double tap. The funnel is also inert during a programmatic `setPlainText` (`_replacingText` guard): the replacement's signals fire with the cursor already over the new text, and a word under a RomanUrdu seed would seed the overlay over text a subsequent region write may tag differently — the same contract as the `_committing` guard around roman-input commits.
- `_isArabicChar` — the word-run scan backing `_wordUnderCursor`, the spell-check candidate scan, and the visual-order word walk — is membership in **`ArabicScriptWordChars`**, the derived table of every letter (`L*`) and combining mark (`M*`) in `ArabicScriptRanges` (Arabic U+0600–06FF, Arabic Supplement U+0750–077F, Arabic Extended-A U+08A0–08FF, and Presentation Forms-A/B U+FB50–FDFF / U+FE70–FEFF): the word class is a definition over Unicode general categories, not a hand-maintained exception list, so digits (`Nd` — U+0660–0669 and U+06F0–06F9), punctuation (`P*`), symbols (`S*`), and format characters (`Cf`) inside those ranges are boundaries. A pasted presentation-form word (`ﻛﺎﻡ`) is therefore still one word, `دوست۵` is `دوست` followed by the digit, and `کام۔` is the word `کام` followed by the mark `۔`, never one word `کام۔`. `ArabicScriptSeparators` is derived the same way (`P*` over the same ranges), so it holds the per-mille and per-ten-thousand signs, the triple dot, the percent sign, the five pointed star, and the ornate parentheses as well as the seven marks the hand list named — and the formatting highlighter's ink rule is built from the same `ArabicScriptRanges` (with an amber rule for U+06F0–06F9 beside the U+0660–0669 one). The invisible joiners (ZWNJ U+200C, ZWJ U+200D, LRM U+200E, RLM U+200F, ALM U+061C) are transparent in `_wordRunAround` through `_continuesWordRun`: a joiner continues a run but is trimmed from both edges, so `ک‌ام` is one word, `‏کام` is the word `کام`, and a run of only joiners is no word at all. `wordRuns` is that same scan run forward: it shares `_continuesWordRun` (membership) and `_trimJoiners` (the edge rule) with `_wordRunAround`, so the point query and the whole-text walk cannot diverge — `testWordRunsAgreesWithThePointQuery` pins it, and it fails if either half is changed in only one of the two. The scan returns the *raw* span, interior joiner included: the widget never rewrites user text, because normalization is a lookup-scope concern, not an editing one — canonicalizing in the buffer would silently alter text under the caret and enter the undo stack. The downstream engine normalizes for it: `RomanAlfaz.hasWord` compares `romanalfaz.urduspell.normalize(word)` against its normalized key set (folding positional and presentation forms, lam-alef ligatures, tatweel, and combining marks — the `urdu-spell` method in `romanalfaz.normalization.NORMALIZATION_METHODS`), and `romanizeArabic` folds through `tafseerUrduAr2Rm`, so `ک‌ام`, `ﻛﺎﻡ`, and `کـام` all reach the dictionary as `کام` and all romanize to `kam`. The separator-key commit gate (`_Separators` = ASCII `string.punctuation` + `string.digits` + space/newline + `ArabicScriptSeparators`) accepts the same marks and every digit, so a typed Arabic separator commits word + mark with both tagged, and a typed digit commits the word with the digit as the separator (substituted to its Eastern Arabic-Indic form in `_writeCommit`; the digit's resync is suppressed in `_commitSeparator` because the digit is a boundary, so the cursor comes to rest past the word's run and a resync would find no word and deactivate the overlay anyway) — the gate and the boundary scan stay in step through the one derived set (`ArabicScriptSeparators`, re-exported from `pyraya` with `ArabicScriptRanges` and `ArabicScriptWordChars`).
- Word walks are **block-local** (A3): a word run cannot cross a block (the block separator is not Arabic), so `_wordUnderCursor` reads the cursor's own block (`findBlock` + block-local positions, re-based to document coordinates), `_adjacentWord` walks neighbour blocks (`block.position() - 1` backwards, `position() + length()` forwards, with the separator slot treated as `len(text)`), and `_activateOverlay`'s romanize + `_wordRect`'s advance fallback slice the word's own block text — no `toPlainText()` copies remain on the word path (the A3 rewrite was once guarded by a whole-document differential, retired after its round per the audit plan; the block-local rule is now pinned by `testAdjacentWordInsideARunReturnsTheContainingRun` and the overlay commit suites). Two guards are load-bearing: in `_wordUnderCursor`, `position < 0 or not block.isValid()` returns early because a document-level `contentsChanged` fires *while a `setPlainText` replacement is mid-flight*, when the cursor position reads -1 and `findBlock` returns an invalid block — the old `toPlainText` walk silently read the last character through Python's negative indexing (wrong but crash-free), the block-local rewrite crashes on the empty text (`text[-1]` IndexError) without the guard; in `_adjacentWord`, a `reference` at the document's inclusive terminator end clamps to the last real character (the pre-A3 version crashed with an IndexError there — caught by the differential the moment it was written).
- Qt's default Left/Right arrow keys move in **logical** character order (Left = position−1, Right = position+1), which is visually flipped in this right-to-left document. The widget therefore intercepts plain Left/Right (no modifiers) in `keyPressEvent` and moves the cursor in visual (screen) order — Left advances the position, Right retreats it — clamped to `characterCount() - 1`; Ctrl/Shift variants fall through to Qt's logical default.
- The overlay's roman word renders in **left-to-right character order** even though the overlay widget is right-to-left laid out and right-aligned (the line only grows leftward as it is typed): position 0 is the visually left edge and the text end the visually right edge. So the line edit's Qt-default in-text Left/Right are already visually correct, and its edge-commit triggers stay Left at position 0 / Right at the text end; an in-text cursor-only key (Left/Right/Home with the cursor between the edges) must not rebuild the suggestion rows: a rebuild re-runs the fuzzy search and resets the highlighted suggestion to the top row, so the row refresh runs in the line edit's `textChanged` handler — which a cursor-only key never fires (F-6) — and precedes the width re-placement, whose width derives from the suggestion list's hint; only the commit target is visual-order — Left at the visually left edge moves to the **next** word, Right at the visually right edge to the **previous** one, landing at that word's edge facing the active word: Left at its start, Right at its end — and the resync re-activates the overlay over the landed word in every case, because `_wordUnderCursor` now accepts the run's end (a cursor at the word's end is over the word); with no adjacent word — the commit lands on a boundary word, whose far side is only whitespace — the overlay is closed and the resync skipped, so the deactivation sticks and the cursor rests at the boundary edge (Left at the word's end, Right at its start). A plain Enter commit likewise skips the resync, so a dismissed overlay is not re-triggered and the cursor rests at the inserted word's end.
- The host rebuilds the suggestion rows and re-places the overlay on every line-edit `textChanged` (`_onOverlayTextChanged`), so its width tracks the typed text: `RomanLineEdit.sizeHint` is the text advance plus the `SuggestionListMargin` margin per side (the shared `SuggestionListMargin` constant, B5 — the list's hint splits the same number), and `_placeOverlay` takes the wider of that and the activation width floor — the word's rect width in scenario 2 (the overlay is never narrower than the Arabic word it covers), or the four-roman-character baseline (`4 * lineEdit.fontMetrics().averageCharWidth()`) for a seeded overlay with no word — so the left edge walks with the text while the right edge and the line edit's top stay pinned at the anchor in both orientations (the overlay's top is the line edit's top in the default orientation, the flipped list's top in the flipped one); the flip itself compares the two list-sized spaces — below (`viewportHeight − top − hint.height() + listHint`, the list's bottom edge in the default orientation) and above (`top − OverlayLayoutSpacing`, the flipped clamp budget — B5's shared `OverlayLayoutSpacing` constant, the gap the overlay's layout, its size hint, and this arithmetic all budget) — flipping only when the list does not fit below *and* the above space is strictly larger, so ties and near-top anchors stay below with the overlay's height clamped to the viewport (the list truncated at the bottom) rather than painting out of bounds at the top; in the flipped orientation the overlay's height is the line edit plus the list clamped to the space above the anchor line, and the line edit is pinned to the anchor line by forcing the overlay's own `QBoxLayout` to resolve for the size just set (`layout().invalidate()` + `layout().activate()` both run while the overlay is hidden), then reading the line edit's settled slot back and shifting the box so the pinning is exact — without the forced activation a re-layout only ever happens for a *visible* parent, so placing a hidden overlay (the click path: a press hides the overlay before the release re-activates it over the word) would answer with the previous word's slots and drag the whole overlay off the word by the slot difference whenever the two words' suggestion lists differ in height. `_syncOverlay` never re-runs while the user edits in the overlay (the document cursor and contents are untouched). When the suggestion list's row count or visibility changes during editing, the overlay's `QVBoxLayout` redistributes the leftover vertical space — QBoxLayout splits it evenly across the layout gaps, which drags the `RomanLineEdit` down away from its top anchor (or, in the flipped orientation, up away from its bottom anchor) (visible at a two-character text, and when the text is empty and the list hides). The overlay's trailing `layout.addStretch()` absorbs all leftover space so the line edit stays pinned to the orientation's outer edge at all times (top in the default, bottom in the flipped); removing it regresses the drift.
- The pinning invariant is absolute: the overlay input stays exactly over the trigger word everywhere and always. `_placeOverlay` pins the overlay's right edge to the word's right edge in both orientations — a word hugging the viewport's right edge (or a typed text wider than the room to its left) clips the overlay on the left rather than pulling the right edge off the word, and a viewport that cannot show the overlay is adjusted (resized or scrolled) by the user, never worked around by moving, clamping, or hiding the overlay away from the word. The active overlay also follows its word on scroll: `PyRaya.__init__` connects `verticalScrollBar().valueChanged` to an argument-free `_onScrollChanged`, which re-places the overlay over its stored anchor; `_ensureOverlay`'s "scrolls with the text automatically" claim is only the small-scroll blit side effect — `QPlainTextEdit`'s viewport `scroll()` moves child widgets with the painted content, but repaint-only jumps and incremental blit drift can leave the overlay a whole line off the word, and only the explicit scroll hook keeps the placement analytical. The hook re-places the overlay while its word is visible — and the off/on-screen decision is the word-rect hit test, never the overlay widget (the overlay reaches further than its word: a flipped suggestion list hangs up into the viewport): in `_repositionActiveOverlay`, the active word's rect — or the seeded anchor line's cursor rect (`QPlainTextEdit.cursorRect(QTextCursor)`) when scenario 1 — is intersected against `viewport().rect()`; a word whose rect is fully outside the viewport deactivates the overlay, and a partially visible word keeps it pinned. The deactivation is two-way: it is a **view suspension**, not a user state — `_suspendedOverlay` remembers `(word, anchorPosition, typedText, documentRevision)`, and the scroll hook and `resizeEvent` dispatch two-way (`_repositionActiveOverlay` when active, `_restoreSuspendedOverlay` when not): a view event that reveals the remembered anchor (a scroll back, a resize grant, a reflow) resumes the overlay as the standard activation (scenario 2 re-romanizes the word, scenario 1 resumes the seeded overlay with its carried-over typed text), with no manual trigger. User decisions outrank the suspension and drop it: every `_deactivateOverlay` funnel call (a mouse press — whose guard therefore also fires over a suspended overlay — Esc/assist-off, the feature switch, boundary-word edge commits, a new activation in `_activateOverlay`/`_activateOverlayAt`), and a document edit while suspended (the remembered revision no longer matches, so the suspension is dropped rather than resumed over text that no longer matches). `_syncOverlay`'s activation is viewport-aware too: a cursor move or keyboard edit landing the cursor on a word that is fully outside the viewport stays quiet (the cursor's position is not a view decision; no popup over an invisible word), and the same-word cursor resync goes through `_repositionActiveOverlay`, so cursor moves honor the hit test and its suspension. The suggestion list's height is also row-quantized: after the forced activation `_placeOverlay` reads the list's actual allocated height and snaps the overlay's height down by `list.height() % list.rowHeight()` (one extra `invalidate()` + `activate()` pass; the `SuggestionList.quantizedHeight` accessor answers the whole-height), so a clamped or truncated placement can never paint a blank strip of list background below its last visible row — the panel ends flush at that row's bottom edge — at the cost of one old artifact: the below-orientation truncation no longer lands the overlay's bottom edge exactly on the viewport's bottom (the row floor wins over the flush fit).
- `RomanOverlay` and `RomanLineEdit` are both mouse-transparent (`Qt.WA_TransparentForMouseEvents`), so `QApplication.widgetAt` over the word returns the document viewport — the document receives real presses, and drags and double-clicks run their default selection; keyboard focus is independent of hit-testing, so the host still calls `setFocus` on the overlay line edit at activation. `PyRaya.mousePressEvent` deactivates the overlay and then sets `_mouseActive`, so `_syncOverlay` early-returns while the button is down (a drag would otherwise reposition the overlay mid-drag, and cross-boundary deactivation would refocus the document); `mouseReleaseEvent` clears the flag after default handling and resyncs — a release on a `roman urdu` word re-activates the overlay (scenario 2) with line-edit focus. The post-commit resync passes `bypassMouse=True`, so the edge-commit cursor jump is still reconciled while the flag is set. Press-point quirk — a press at `_wordRect(...).right()` (1 px inside the exclusive right edge) lands the cursor inside the word (at its start), a press at the visual center of a short word lands after the word (on the trailing space, i.e., at the word's end: the release resync re-activates the overlay over it), and a release at `_wordRect(...).left() + 1` lands at the word's end.
- The spell-check pass invokes the engine provider only after its candidate scan (`wordRuns` over the block — the same walk `PyRaya.wordRuns` exposes; both ends resolving RomanUrdu, stored tag or the seed) finds at least one candidate — the scan resolves the ends' kinds from the block's format runs (one document-format read per run; A2), not per candidate. — the engine (and its ~0.3 s dictionary cold load) is created on the first re-highlight containing such a word, never for a textless widget. The laziness is load-bearing: `RomanAlfaz` rebuilds its index on any local `Vocabulary` change, and the pinned wheel hard-asserts `undef == 0` over the counter's keys (a `Vocabulary.add` of a roman key stores the roman key), so constructing the engine eagerly in `PyRaya()` would turn a user's `localDictionary()` edit into an `AssertionError`.
- The venv stubs declare `QTextLayout.FormatRange`'s attributes (`format`, `start`, `length`) as `...` with `# type:` comments that pyrefly does not honor (unlike Pyright): reads must cast the attributes to their documented runtime types (`QTextCharFormat` / `int`), and any assignment to them carries `# pyrefly: ignore [bad-assignment]` (see `_copyFormatRange`) — nothing is assignable to an `Ellipsis`-typed attribute, so a cast does not help there.
- **`QDialogButtonBox` button wiring** — `QDialogButtonBox.clicked` emits `clicked(QAbstractButton*)`: one argument, no `StandardButton` overload, so `_onButtonClicked` takes a single `button` and matches by identity against `self._buttons.button(...)` (a two-argument handler `TypeError`s on every click — caught by `testDialogOkButtonAcceptsAndCancelButtonRejects`, which clicks the real buttons rather than monkeypatching `exec`). In PySide6 6.11.2 the box's automatic connection to the parent `QDialog`'s `accept()`/`reject()` does not fire (plain `QDialog` + `ok.click()` leaves the dialog open with `result()` unset), so the explicit handler is load-bearing: without it the dialog would never close. Relatedly, PySide6 *swallows* exceptions raised in Python signal slots (prints them and continues the emission), so a `TypeError`-raising handler can still leave the dialog half-behaving while the traceback only shows up on stderr; and `QAbstractButton.click()` on a **disabled** button emits no `clicked` at all (a dialog test that prefills an unmappable word gets a disabled OK and a silent no-op click — prefill a mappable word, e.g. `قلم`).
